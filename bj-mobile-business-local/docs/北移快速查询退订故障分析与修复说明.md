# 北移快速查询退订故障分析与修复说明

## 1. 结论

退订失败的直接原因是当前实现构造了错误的门户业务参数。当前代码把列表下标、`xh` 等展示定位值放入 `field1`，同时额外提交 `ywCode`；北京移动原页面的默认退订协议则要求只提交 `phoneNum`、`brand`、`field1`，其中 `field1` 是当前业务的 `ywCode`。套餐类数据没有 `ywCode` 时，使用对应的 `offerId` 作为业务编码。

因此，门户接口虽正常完成了 AES 加密、鉴权、WAF 校验和 HTTP 调用，但后端实际收到的是错误的业务标识，最终由 `OPF_SO_PERSON_UNIFORM_DEL_001` 返回“该活动不允许线上退订”。该提示在本次故障中不能证明业务本身不可退订。

## 2. 分析材料

- 成功请求：`bmcc退订.har`
- 成功项目源码：`bmcc查询退订.zip`
- 当前实现：`backend/src/services/portalClient.js`
- 当前运行日志：`backend/logs/app.log`

HAR 中依次包含查询、退订、再次查询三个请求，接口分别为：

1. `POST /portal-bff/api/packageQuery/v1.0/index`
2. `POST /portal-bff/api/packageQuery/v1.0/unsubscribe`
3. `POST /portal-bff/api/packageQuery/v1.0/index`

HAR 请求体和响应体均为 AES 密文，且 HAR 不包含浏览器会话内随机生成的 `portalKey`，所以不能仅凭该 HAR 还原明文。不过，请求路径、方法、密文长度和配套前端源码足以确认协议结构。

成功 HAR 的退订请求解码后是 80 字节 AES 密文。以 11 位手机号、中文品牌和 12 位业务编码计算，`{ phoneNum, brand, field1 }` 明文加 PKCS#7 填充后正好占 80 字节；修复前再加入独立 `ywCode` 字段会跨入下一个 AES 分组。该长度关系与成功源码的三字段请求一致。

## 3. 成功源码中的协议

默认访问 `/nwt/portal/packageQuery` 时，页面加载 `index201603` 组件。选择增值业务后，源码执行的等价逻辑为：

```js
selectedCode = item.ywCode

PackageQuery.packageQueryUnsubscribe({
  phoneNum,
  brand,
  field1: selectedCode,
})
```

接口声明为 `POST`，请求对象通过 `data` 发送。请求中没有单独的 `ywCode` 字段。

源码还包含一个仅在 URL 显式指定 `pageVersion=oldPage` 时使用的替代页面。该页面对增值业务把列表的 1 基位置传入 `field1`。当前前端查询没有传 `oldPage`，HAR 的 Referer 也没有该参数，因此当前流程应使用默认页面的业务编码协议。修复仍保留了显式 `oldPage` 的位置映射，以免该兼容入口回归。

## 4. 当前实现的问题

修复前的核心逻辑等价于：

```js
field1 = business.field1 || business.originalIndex || business.xh || business.index
ywCode = business.ywCode || business.offerId

payload = { phoneNum, brand, field1, ywCode }
```

同时，业务归一化又执行：

```js
field1 = item.field1 || item.xh || String(arrayIndex)
```

这造成两个问题：

1. `field1` 被赋成展示序号，而不是门户退订业务编码。
2. 请求多出成功源码未定义的 `ywCode` 字段。

日志中的实际失败样本也符合该特征。例如套餐 `offerId=111603018812` 被提交为 `field1=3`；另一些增值业务则把 `xh` 提交为 `field1`。接口已经进入业务删除服务后才拒绝，说明登录、加密、请求路径和传输链路不是本次失败的根因。

## 5. 修复设计

- 新增独立的 `unsubscribeCode`，明确表示门户退订协议中的业务标识。
- 默认页面的增值业务使用 `ywCode`，套餐使用 `offerId`。
- `originalIndex` 和 `xh` 只保留为展示/诊断信息，不再作为默认退订业务编码。
- 退订请求严格只发送 `phoneNum`、`brand`、`field1`。
- 没有业务编码时仍允许用户手工输入后尝试提交。
- 退订确认弹窗展示最终提交的 `phoneNum`、`brand`、`field1`，三个参数均可在本次提交前修改。
- 所有查询结果继续显示退订按钮，不依据前端资格字段拦截；最终是否允许退订由门户响应决定。
- 保留门户返回的具体拒绝信息，便于区分参数错误与真实业务限制。

## 6. 验证范围

自动化测试覆盖：

- 增值业务 `ywCode -> field1`
- 套餐 `offerId -> field1`
- `xh`、数组下标不会覆盖默认业务编码
- 请求体不包含额外 `ywCode`
- 缺少编码时支持手工输入
- `pageVersion=oldPage` 的 1 基位置兼容
- 成功和拒绝响应的判定及消息保留

验证不会发起真实退订。真实环境最终仍可能因合约、违约金、渠道限制或门户策略返回不可退订；此类业务拒绝应以修复后门户返回为准。

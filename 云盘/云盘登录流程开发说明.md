# 中国移动云盘 H5 登录流程开发说明

本文基于 `云盘/` 目录中的 HAR 抓包与前端构建源码整理，重点覆盖验证码、短信登录、接口加密、登录态存储、Authorization 使用、ssoToken 获取与跳转认证。示例中的手机号、token、cookie 均做脱敏处理，开发时以实时接口返回为准。

## 1. 项目材料概览

核心材料：

- `云盘/yun.139.com/m/index.html`：H5 入口。
- `云盘/yun.139.com/m/static/js/app.5381989f.js`：主 bundle，包含接口封装、Axios 拦截器、Vuex auth 模块、加密工具。

- `云盘/login.har`：短信验证码登录示例。
- `云盘/queryAvailableBenefit.har`、`云盘/云盘请求分析.har`：登录后业务接口示例。

## 2. 登录主流程

整体链路：

1. 打开 H5，初始化设备信息、基础 Header、风控/埋点 Cookie。
2. 如需要滑块验证，调用阿里云验证码 `InitCaptchaV3`，用户完成后调用 `VerifyCaptchaV3`，拿到 `securityToken`/`VerifyCode`/`certifyId`。
3. 发送短信验证码。短信接口请求体使用用户域固定 AES-CBC 加密；如果带滑块结果，会把滑块校验值放入短信请求参数。
4. 用户输入短信验证码后，重新请求云盘 RSA 公钥，生成本轮专用的 16 位 AESKey。
5. 组装登录业务 JSON，用 AES-ECB/PKCS7 加密得到 `encryptMsg`。
6. 用本轮 RSA 公钥加密同一个 AESKey，作为请求头 `mcloud-skey`。
7. 请求登录接口，登录成功后得到 `token`、`authToken`、账号信息、用户域信息、路由域名信息。
8. 前端保存登录态，并生成 `Authorization: Basic base64("pc:<account>:<authToken>")`。
9. 后续普通业务接口带 `Authorization`，部分跳转页面额外通过 `querySpecToken/querySpecTokenV2` 获取 ssoToken。

## 3. 接口清单

### 3.1 获取 RSA 公钥

抓包：`云盘/getRsaPublicKey.har`

```http
POST https://yun.139.com/orchestration/auth-rebuild/key/v1.0/getRsaPublicKey
Content-Type: application/json;charset=UTF-8
```

请求体：

```json
{
  "clientCode": "10601",
  "type": 1
}
```

响应核心字段：

```json
{
  "success": true,
  "code": "0",
  "data": {
    "result": {
      "resultCode": "0",
      "resultDesc": "success"
    },
    "publicKey": "MIGfMA0GCSqGSIb3DQEBAQUAA4GN..."
  }
}
```

用途：登录前生成 `mcloud-skey`。7.17.10 Web 登录组件会在每次登录尝试前调用 `getSecretKey({ clientCode, type: 1 })`，获取公钥并准备 AESKey；本地持久化中的旧 RSA/AES 只能用于诊断，不能跨登录轮次复用。

### 3.2 阿里云滑块验证码

抓包：`云盘/captcha.har`

初始化：

```http
POST https://7elm7k.captcha-open.aliyuncs.com/
Content-Type: application/x-www-form-urlencoded; charset=UTF-8
Action=InitCaptchaV3
SceneId=1rmw421p
```

校验：

```http
POST https://7elm7k-verify.captcha-open.aliyuncs.com/
Content-Type: application/x-www-form-urlencoded; charset=UTF-8
Action=VerifyCaptchaV3
```

校验成功响应包含：

```json
{
  "Success": true,
  "Result": {
    "securityToken": "...",
    "VerifyCode": "T001",
    "VerifyResult": true,
    "certifyId": "..."
  }
}
```

源码里短信发送参数名是 `puzzleVerfycode`/`puzzleVerfyCode`，注意拼写里是 `Verfy`，不是标准 `Verify`。短信登录页面在触发风控错误后会展示滑块，滑块成功后再重发短信。

### 3.3 获取短信验证码

抓包：`云盘/getSmsCode.har`

```http
POST https://user-njs.yun.139.com/user/sms/getSmsCode
Content-Type: application/json;charset=UTF-8
```

国内号码源码预加密前的业务体大致为：

```json
{
  "account": "<手机号>",
  "reqType": 3,
  "puzzleVerfyCode": "<滑块结果，可选>"
}
```

香港/巴基斯坦号码走另一套字段：

```json
{
  "phoneNumber": "<手机号>",
  "reqType": 3,
  "random": "<16位随机串>",
  "nationCode": "+852 或 92",
  "clientType": "<clientType>",
  "puzzleVerfycode": "<加密后的滑块结果，可选>"
}
```

抓包里该接口的请求体和响应体都是加密字符串，不是明文 JSON。前端在请求拦截器里会对特定接口做加密转换，因此不要直接照抄 HAR 中的密文；密文和 AESKey、时间、随机串、滑块结果相关。

### 3.4 登录

抓包：`云盘/login.har`

```http
POST https://yun.139.com/orchestration/auth-rebuild/permission/v1.0/login
Content-Type: application/json;charset=UTF-8
mcloud-skey: <RSA(publicKey, AESKey)>
```

短信登录预加密业务体：

```json
{
  "account": "<手机号>",
  "dycPwd": "<短信验证码>",
  "loginStyle": "passSMS",
  "verifyCode": "<可选>",
  "ifOpenAccount": "1",
  "verType": 2,
  "clientEnv": "3",
  "setCookie": 0
}
```

最终发送体：

```json
{
  "encryptMsg": "<AES-ECB-PKCS7(JSON.stringify(业务体), AESKey)>",
  "clientId": "10701",
  "autoLogin": true,
  "returnToken": true
}
```

登录成功响应核心字段：

```json
{
  "success": true,
  "code": "0",
  "data": {
    "result": { "resultCode": "0", "resultDesc": "请求成功" },
    "nationCode": "+86",
    "token": "<加密 token>",
    "authToken": "<明文业务 authToken>",
    "cutoverStatus": 1,
    "belongsPlatform": 2,
    "userDomainId": "...",
    "userid": "...",
    "simplifyAccount": "152****4812",
    "encryptAccount": "base64手机号",
    "routerInfo": []
  }
}
```

重要：登录响应中的 `token` 不是 ssoToken。源码把 `authToken` 作为业务 Authorization 的核心，把 `token` 作为加密 token 保存。需要跳转认证时再请求 `querySpecToken/querySpecTokenV2`。

## 4. 加密与签名方法

### 4.1 AES 登录体加密

源码：`app.5381989f.js:64040`

```js
AES.encrypt(plainText, Utf8.parse(aesKey), {
  mode: CryptoJS.mode.ECB,
  padding: CryptoJS.pad.Pkcs7
}).toString()
```

规则：

- `aesKey` 是 16 位随机字符串。
- 明文是 `JSON.stringify(业务体)`。
- 模式是 ECB，无 IV。
- 输出是 Base64 字符串。

解密：

```js
AES.decrypt(cipherText, Utf8.parse(aesKey), {
  mode: CryptoJS.mode.ECB,
  padding: CryptoJS.pad.Pkcs7
}).toString(CryptoJS.enc.Utf8)
```

### 4.2 RSA 加密 AESKey

源码：`app.5381989f.js:64036`

```js
const jsEncrypt = new JSEncrypt()
jsEncrypt.setPublicKey(publicKey)
const mcloudSkey = jsEncrypt.encrypt(aesKey.toString())
```

登录、重置密码等接口通过请求头传：

```http
mcloud-skey: <mcloudSkey>
```

同时源码会把该值保存为 `secretKey`，Cookie/Storage key 是 `skey`。

### 4.3 mcloud-sign

源码：`app.5381989f.js:64010`、`app.5381989f.js:56591`

请求拦截器会生成：

```http
mcloud-sign: <timestampLike>,<8位随机串>,<MD5签名>
```

签名算法：

```js
body = JSON.stringify(data || {})
body = encodeURIComponent(body)
bodySorted = body.split('').sort().join('')

c = MD5(Base64.encode(bodySorted))
u = MD5(timestampLike + ':' + random8)
sign = MD5(c + u).toUpperCase()
```

其中 `timestampLike` 来自源码 `Object(f.o)(new Date().getTime(), "", "", "")`，抓包格式类似 `20260707000123`。实际实现要复用源码函数或完全对齐它的时间格式。

### 4.4 Basic Authorization

源码：`app.5381989f.js:64192`

```js
Authorization = 'Basic ' + base64('pc:' + account + ':' + authToken)
```

抓包中也能看到：

```http
Authorization: Basic cGM6<base64...>
```

部分接口使用 `mobile:<account>:<authToken>`，但 H5 登录态生成默认是 `pc:<account>:<authToken>`。不要把 `token` 字段误当成 `authToken`。

## 5. 登录态存储与使用

### 5.1 Vuex auth 字段

源码：`app.5381989f.js:56850`

核心字段：

- `account`：脱敏账号，如 `152****4812`。
- `completeAccount`：完整手机号。
- `authToken`：解密后的业务 token。
- `token`：加密 token。
- `authorization`：Basic Authorization。
- `belongsPlatform`：平台标识。
- `cutoverStatus`：用户域/切流状态。
- `userDomainId`：用户域 ID。
- `AESKey`：登录加密用 AESKey。
- `RSAKey`：RSA 公钥。
- `secretKey`：RSA 加密后的 AESKey，也就是 `mcloud-skey`。
- `nationCode`：国家码。

### 5.2 Cookie/LocalStorage key

源码常量：`app.5381989f.js:108109`

常见 key：

- `ORCHES-I-ACCOUNT-SIMPLIFY`：脱敏账号。
- `ORCHES-I-ACCOUNT-ENCRYPT`：Base64 完整账号。
- `ORCHES-C-TOKEN`：AESKey。
- `token`：加密 token。
- `auth_token`：authToken。
- `authorization`：Basic Authorization。
- `a_k`：RSA 公钥缓存。
- `skey`：RSA 加密后的 AESKey。
- `cutover_status`：切流状态。
- `platform`：平台。
- `NATION_CODE`：国家码。
- `ud_id`：用户域 ID。
- `ORCHES-USER-ID`：用户 ID。

登录成功后源码逻辑：

- 从响应的 `simplifyAccount/encryptAccount` 或旧缓存恢复账号。
- `token` 和 `authToken` 都存在时，`token` 保存为加密 token，`authToken` 保存为明文业务 token。
- 如果只有一个 token，会用 AES 加/解密补齐另一个。
- 根据完整账号和 `authToken` 生成 `Authorization`。
- 保存 `routerInfo` 到 `localStorage.routerInfo`，后续模块域名可能来自这里。

## 6. ssoToken 获取与跳转认证

### 6.1 ssoToken 来源

源码里出现 `ssoToken` 的地方不是登录响应解析，而是跳转链接拼装：

```js
// app.5381989f.js:13186 起
{ phoneNumber: completeAccount, toSourceId: '001003' }
```

调用成功后取：

```js
token = response.data.token
```

然后：

- 如果链接里有 `#ssoToken#`，替换为 `token`。
- 如果链接里有 `#rcsToken#`，也替换为该 `token`。
- 如果没有占位符，则给 URL 追加 `ssoToken=<token>`。
- 同时替换或追加 `account=<completeAccount>`。

相关接口封装有两类：

```http
POST https://yun.139.com/orchestration/auth-rebuild/token/v1.0/querySpecToken
```

以及用户域接口：

```http
POST <user-domain>/querySpecTokenV2
```

源码中 `querySpecToken` 封装见 `app.5381989f.js:86657`；`querySpecTokenV2` 封装见 `app.5381989f.js:107689`。项目中落地文件 `云盘/yun.139.com/orchestration/auth-rebuild/token/v1.0/querySpecToken.html` 是该接口示例。

### 6.2 ssoToken 与登录 token 的区别

- `authToken`：登录成功后返回，业务接口 Authorization 使用它。
- `token`：登录成功后返回的加密 token，前端保存为 `token`。
- `ssoToken`：跳转到特定外部/会员/活动页面前，通过 `querySpecToken` 或相关业务接口临时获取的跳转 token。
- `cookieToken`/`cookieTokenKey`：抓包 Cookie 中存在，偏自动登录/SSO Cookie 态；不能替代 `authToken`，也不等同于 ssoToken。

### 6.3 使用示例

原始跳转链接：

```text
https://example.yun.139.com/page?token=#ssoToken#&account=#account#
```

前端处理后：

```text
https://example.yun.139.com/page?token=<querySpecToken返回token>&account=<完整手机号>
```

如果没有占位符：

```text
https://example.yun.139.com/page
```

会追加：

```text
https://example.yun.139.com/page?ssoToken=<token>&account=<完整手机号>
```

## 7. 开发注意事项

1. 不要直接复用 HAR 里的密文。短信和登录接口密文依赖 AESKey、RSA 公钥、设备、时间、随机数和滑块结果，重放很容易失败。
2. 每次登录尝试前重新请求 RSA 公钥并生成新的 16 位 AESKey；`mcloud-skey` 必须与当前 `encryptMsg` 使用同一轮 AESKey。不要跨登录轮次复用磁盘中的 RSA/AES 材料。
3. `mcloud-sign` 需要跟请求体同步。body 变了签名也要变，尤其是 `returnToken/autoLogin/setCookie` 这类字段。
4. 登录接口 `returnToken: true` 很关键。没有它，响应可能缺少后续跳转所需的 token 数据。
5. `autoLogin: true` 只在非短信验证码发送、非重置密码、非二次校验等登录场景下附加。
6. `authToken` 和 `token` 不要混用。业务 Authorization 使用 `authToken`；跳转 ssoToken 通过接口另取。
7. 国家码会影响短信接口字段。`+86`、`+852`、`92` 分支字段不同，滑块字段加密方式也不同。
8. `puzzleVerfycode/puzzleVerfyCode` 拼写不统一，照源码字段走，不要自行改成 `Verify`。
9. `routerInfo` 很重要。登录后不同模块接口域名可能来自响应的 `routerInfo`，不能硬编码单个域名。
10. 用户域切流状态 `cutoverStatus=1` 时，部分目录和接口路径走新体系，旧路径可能返回未登录或资源不存在。
11. 业务接口失败遇到 401/登录失效时，源码会清理登录态并跳转 `/autoLogin?redirectPage=custom`，开发调试时要看是否被自动清态。
12. 抓包 Cookie 中的 `mc_at/mc_bt/cookieToken/cookieTokenKey/skey/a_k` 与登录态有关，但不是所有接口都必须手工设置；浏览器场景应让同域 Cookie 自然携带。

## 8. 后端复刻建议

如果要在本地后端实现登录代理，建议拆成这些模块：

- `deviceProfile`：统一生成 `x-DeviceInfo`、`x-yun-client-info`、客户端版本、渠道。
- `crypto`：实现 AES-ECB/PKCS7、RSA 公钥加密、Basic Authorization、mcloud-sign。
- `captcha`：封装阿里云验证码初始化和校验结果透传。
- `authClient`：封装 `getRsaPublicKey`、`getSmsCode`、`login`、`querySpecToken`。
- `sessionStore`：保存完整账号、脱敏账号、authToken、token、authorization、AESKey、RSAKey、secretKey、routerInfo、userDomainId、cutoverStatus。
- `requestClient`：所有业务接口统一从 session 注入 Authorization 和公共 Header。

最小可用登录伪代码：

```js
const publicKey = await getRsaPublicKey()
const aesKey = randomString(16)

const loginPayload = {
  account: phone,
  dycPwd: smsCode,
  loginStyle: 'passSMS',
  ifOpenAccount: '1',
  verType: 2,
  clientEnv: '3',
  setCookie: 0
}

const body = {
  encryptMsg: aesEcbPkcs7Encrypt(JSON.stringify(loginPayload), aesKey),
  clientId: '10701',
  autoLogin: true,
  returnToken: true
}

const headers = {
  ...commonHeaders(body),
  'mcloud-skey': rsaEncrypt(aesKey, publicKey)
}

const loginResp = await post(LOGIN_URL, body, headers)
const account = loginResp.data.encryptAccount
  ? base64Decode(loginResp.data.encryptAccount)
  : phone
const authToken = loginResp.data.authToken || aesDecrypt(loginResp.data.token, aesKey)
const authorization = 'Basic ' + base64Encode(`pc:${account}:${authToken}`)
```

获取 ssoToken：

```js
const specTokenResp = await post(
  'https://yun.139.com/orchestration/auth-rebuild/token/v1.0/querySpecToken',
  { account, toSourceId: '001003' },
  { Authorization: authorization, ...commonHeaders() }
)

const ssoToken = specTokenResp.data.token
```

## 9. 调试避坑指南

- 登录成功但业务接口 401：优先检查 `Authorization` 是否按 `pc:<完整手机号>:<authToken>` 生成，而不是用了脱敏号或加密 `token`。
- 登录成功但跳转页未登录：检查是否调用了 `querySpecToken`，并确认跳转链接使用的是 `ssoToken` 而不是登录响应的 `token`。
- 短信接口返回风控错误：需要先跑滑块流程，把滑块校验结果带入短信请求。
- 登录接口提示解密失败或参数错误：检查 AES 模式是否 ECB/PKCS7、AESKey 是否 16 位、`mcloud-skey` 是否用同一个 AESKey 生成。
- 接口签名失败：检查 `mcloud-sign` 是否在 body 最终形态之后生成，body 加密/转换后不要再改。
- 用户域接口异常：检查 `routerInfo`、`userDomainId`、`cutoverStatus` 是否已保存并注入。
- 本地代理跨域异常：浏览器直连依赖同域 Cookie，后端代理需要自己维护 CookieJar。
- 多账号调试串号：切换账号前清理 `authorization`、`auth_token`、`token`、`ORCHES-I-ACCOUNT-*`、`ud_id`、`routerInfo`。

## 10. 结论

云盘 H5 登录不是单纯的短信验证码登录，而是“短信/滑块风控 + AES 业务体加密 + RSA 包装 AESKey + mcloud-sign + 登录态 Cookie/Storage + ssoToken 二次换取”的组合流程。开发时最容易混淆的是 `authToken`、`token`、`ssoToken` 三者：业务请求用 `authToken` 生成 Authorization，跳转认证用 `querySpecToken` 返回的 token，登录响应的 `token` 主要是前端保存的加密 token。

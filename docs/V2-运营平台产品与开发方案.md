# CMCC 运营平台 V2 产品与开发方案

## 1. 改版目标

本轮改版覆盖三个相互协作的产品：

1. Cookie Ops V2：降低账号凭据维护、全球通 Token 获取和已订业务查询的操作成本。
2. QQT Rights V2：把抢购工具从“参数表单”重构为可观察、可追溯的任务工作台，并明确任务只在部署服务器本地执行。
3. Project Ops V2：从单口令管理台升级为支持多管理员、角色和项目范围的运维控制台。

V1 页面与接口继续保留，V2 通过独立路由进入。数据层和任务执行层复用现有实现，避免双套数据源。

## 2. 设计原则

- 先给状态，再给动作：用户进入页面先看到健康、风险和正在执行的任务。
- 高频动作一步完成：复制 Token、刷新 CK、同步账号、重跑任务均放在结果附近。
- 危险动作显式确认：删除账号、停止任务、部署和重置密码必须二次确认。
- 长任务可观察：展示排队、准备、执行、后检和结果阶段，不用无反馈的全屏等待。
- 凭据最小暴露：页面默认脱敏；密码只写入哈希；Token 仅在用户主动复制时进入剪贴板。
- 执行位置可验证：QQT 任务记录主机、PID、执行器和 worker 绝对路径。

## 3. Cookie Ops V2 增量设计

### 3.1 全球通 Token 任务结果

任务详情在 `刷新 CK`、`刷新并签到`、`CK 维护`完成后增加主操作“复制有效 Token”。

```text
┌ 任务详情 ─────────────────────────────┐
│ 刷新并签到                         成功 │
│ 18 / 20    成功 18  跳过 2             │
│                                        │
│ [复制有效 Token]  已筛除过期/已领取账号 │
└────────────────────────────────────────┘
```

交互规则：

- 点击后请求严格 Token 导出接口，不再次刷新 CK，避免结果页产生新的长任务。
- 只复制仍在有效窗口、全球通身份已确认、当月及拼图权益未领取的 Token。
- 多个 Token 使用换行分隔；按钮反馈复制数量；无可用 Token 时显示明确原因。
- 不在 DOM、日志或提示中回显 Token。

### 3.2 已订业务进入链路

统一流程：

```text
选择账号 -> 强制刷新/恢复 10086 CK -> 置换 touch/shop CK
         -> 校验 shop CK -> 创建短期查询会话 -> 查询已订业务
```

- 进入页面时展示当前阶段，避免用户把上游置换耗时误认为页面卡死。
- 旧的 `cmccAppCookie` 只能作为故障诊断信息，不再跳过 10086 CK 刷新链路。
- 刷新失败时提示“CK 刷新失败”；置换失败时提示“商城登录态置换失败”，错误阶段可区分。
- 置换成功后保存最新 shop CK，后续查询和退订复用当前短期会话。

## 4. QQT Rights V2 信息架构

V1：`/`；V2：`/v2/`。

| 页面 | 用户问题 | 核心内容 | 主操作 |
| --- | --- | --- | --- |
| 总览 | 现在能不能执行 | 节点状态、任务数、最近运行、账号可用数 | 新建任务 |
| 任务 | 什么时候跑、跑得怎样 | 任务筛选、进度、执行节点、结果摘要 | 运行/重跑/停止 |
| 账号 | 哪些 Token 可用 | CMCC 同步结果、有效期、领取状态 | 同步有效 Token |
| 日志 | 为什么失败 | 结构化阶段、服务器时间、worker 输出 | 刷新/复制诊断摘要 |
| 系统 | 到底在哪里执行 | 主机、PID、绑定地址、worker 路径、上游延时 | 运行自检 |

### 4.1 总览原型

```text
┌ QQT Rights V2 ─────────────────────────────────────────┐
│ 总览  任务  账号  日志  系统                  [V1] [退出] │
├─────────────────────────────────────────────────────────┤
│ 运行节点：本机 Mac mini · PID 1234 · 受管实例           │
│ [新建抢购任务] [同步 Cookie Ops Token]                  │
│                                                         │
│ 运行中 1   今日完成 8   有效账号 26   最近成功率 92%     │
│                                                         │
│ 当前任务 ───────────────  最近结果 ──────────────────── │
│ 10:00 场次  16/26  61%    09:00  成功 24/26             │
└─────────────────────────────────────────────────────────┘
```

### 4.2 新建任务交互

使用三步抽屉而不是一张超长表单：

1. 选择活动：普通全球通、行动计划、周三充值。
2. 选择账号：从 Cookie Ops 同步有效 Token，或使用当前已导入账号。
3. 执行策略：立即/定时、Python/Go/Java、并发、轮询和高级参数。

最后一步固定展示执行摘要和“任务将在服务器本地执行”的节点标识。高级参数默认收起。

### 4.3 本地执行保证

- 浏览器只提交任务配置，不包含 worker 代码，也不直接请求活动上游。
- FastAPI 在部署服务器内通过绝对路径启动 Python/Go/Java worker。
- 每个任务写入 `execution_node`：主机名、服务 PID、worker PID、worker 路径、开始时间。
- 服务只绑定 `127.0.0.1:8899`，公网经 Cloudflare Tunnel 和 Nginx 反向代理进入。
- 启动脚本禁止再创建 `0.0.0.0:8899` 的旁路实例；部署后只允许一个监听进程。

## 5. Project Ops 多管理员设计

### 5.1 角色模型

| 角色 | 权限 |
| --- | --- |
| Owner | 查看和操作所有项目；创建、停用、重置管理员；调整项目范围 |
| Operator | 查看控制台；只对授权项目执行启动、重启、检测、构建和部署 |
| Viewer | 只查看授权项目状态、日志和操作记录 |

账号字段：`username`、`displayName`、`role`、`serviceIds`、`disabled`、`passwordHash`、`createdAt`、`updatedAt`、`lastLoginAt`。

### 5.2 登录与账号管理

- 登录由单密码升级为“用户名 + 密码”，旧部署自动生成 `admin` Owner，密码沿用当前管理口令。
- Owner 在“系统 > 管理员”中创建账号，首次设置至少 12 位密码。
- 密码使用 Node.js `scrypt` + 独立随机盐保存，不保存或返回明文。
- 重置密码后撤销该管理员的全部会话；停用账号立即撤销会话。
- 禁止删除当前登录账号和最后一个可用 Owner。
- Operator/Viewer 的服务列表和操作入口按 `serviceIds` 过滤，后端再次校验，不能依赖前端隐藏。

### 5.3 管理页面原型

```text
系统 / 管理员
┌─────────────────────────────────────────────────────────┐
│ 管理员账号                                   [新增管理员] │
├──────────┬──────────┬────────────┬───────────┬───────────┤
│ 用户名   │ 角色     │ 项目范围   │ 最近登录  │ 操作      │
│ admin    │ Owner    │ 全部       │ 2 分钟前  │ 编辑      │
│ cookieop │ Operator │ Cookie Ops │ 昨天      │ 编辑/停用 │
└──────────┴──────────┴────────────┴───────────┴───────────┘
```

## 6. 开发与迁移方案

### 6.1 数据迁移

- Cookie Ops 不新增数据库表，复用 Token 导出与账号凭据字段。
- QQT V2 复用 `jobs.json`、日志目录和授权密钥；新增运行节点元数据，旧任务兼容缺省值。
- Project Ops 管理员保存于权限为 `0600` 的运行时 JSON；首次启动从 `.env` 引导 Owner。

### 6.2 发布顺序

1. 发布 Cookie API 顺序修复和 V2 复制按钮，运行类型检查、API/UI 测试与生产构建。
2. 停止 QQT 旁路旧实例，发布 V2 静态资源和运行元数据接口，重启唯一 PM2 实例。
3. 发布 Project Ops 多管理员后端，再切换登录页和系统管理界面。
4. 分别验证本机端口、Nginx Host 路由和公网 HTTPS；保存 PM2 状态。

## 7. 验收标准

- Cookie Token 任务完成后可一键复制，剪贴板数量与接口返回总数一致。
- 每次进入商城已订业务都先发生 10086 CK 刷新/恢复，再发生 shop 置换。
- 8899 仅一个监听 PID，任务详情展示的主机和 worker 路径属于部署服务器。
- QQT V1、V2 均可进入，V2 在手机和桌面均无横向溢出或控件重叠。
- Project Ops 支持至少两个管理员同时登录，项目范围在 API 层生效。
- 密码、Token、Cookie 不出现在接口列表、日志、DOM 和 Git 跟踪文件中。

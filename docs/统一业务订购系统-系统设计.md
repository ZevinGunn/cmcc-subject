# 统一业务订购系统设计文档

版本：V1.0  
日期：2026-07-24  
系统：北京移动业务查询与统一快捷订购工作台

## 1. 设计目标

在现有 `bmcc.1008086.xyz` 查询退订系统中增加一个可操作的统一订购工作台，使操作员能够在同一界面完成北移、中移商城和网格通业务的准备、选档、协议确认、短信和最终订购，同时不掩盖三套上游协议之间的差异。

成功标准：

- 三个平台都有完整、可执行的向导，不是接口调试表单。
- 同一个公共状态和错误模型支持页面恢复、倒计时、结果展示。
- 平台原始凭据不进入浏览器持久化、日志或最终结果。
- 所有自动化测试可离线完成，不访问真实上游。
- 不确定结果绝不被显示为失败后可重试。

## 2. 系统上下文

```text
操作员浏览器
  |
  | HTTPS /api/quick-orders
  v
Express 统一订购域
  |-- 公共状态机 / 锁 / 幂等 / 脱敏
  |-- 北移适配器 ---- 现有北京移动登录会话 ---- service.bj.10086.cn
  |-- 中移适配器 ---- 临时商城 Cookie/SSO ------ wx.10086.cn
  `-- 网格通适配器 -- 临时入口表单会话 -------- ysmapp.bj.10086.cn
```

`cookie-app` 是参考实现和未来可选的账号桥，不作为统一系统的运行时数据库依赖。这样可以避免跨项目读取凭据、权限模型耦合和部署顺序依赖。

## 3. 模块设计

### 3.1 后端

| 模块 | 职责 | 不负责 |
|---|---|---|
| `quickOrders/catalog` | 平台/产品目录、能力和风险提示 | 上游网络访问 |
| `quickOrders/sessionStore` | TTL、私有上下文、公共视图 | 持久化未完成订单 |
| `quickOrders/service` | 状态校验、适配器调度、锁、幂等 | 平台字段拼装 |
| `adapters/north` | 专用初始化、门户提交和短信确认 | 商城/网格通协议 |
| `adapters/retail` | 商城 SSO、加密、产品、规格、协议、短信和订单 | 账号库管理 |
| `adapters/grid` | 入口解析、表单会话、档位、挑战、token 和结果页 | 生成推荐入口 |
| `routes/quickOrders` | HTTP 输入、错误和响应包装 | 业务成功猜测 |

### 3.2 前端

`QuickOrderPage.vue` 由以下区域组成：

1. 顶栏：返回、页面名、当前登录号码状态。
2. 平台分段控件：北移、中移商城、网格通。
3. 平台接入区：北移显示当前门户会话；中移输入 Cookie；网格通输入手机号和入口 URL。
4. 固定步骤条：接入、产品、确认、短信、结果。
5. 产品区：业务信息、资格、动态档位、费用和风险。
6. 协议区：实时协议内容和同意复选框。
7. 动作区：按当前阶段只显示一个主操作，短信重发为次操作。
8. 最终确认弹窗：二次列出真实订购信息。
9. 结果区：成功、明确拒绝或结果未知。

不在页面显示协议密钥、请求 payload、原始响应或调试字段。已有自定义订购面板保留给高级排障，但导航的主入口指向统一工作台。

## 4. 页面信息架构

### 4.1 导航

在已登录业务页和登录页工具区增加“快捷订购”入口。北移依赖现有登录会话；中移和网格通允许从登录页进入，但如果已有北京移动会话仍显示当前号码供核对。

哈希路由：

```text
#/quick-order
```

### 4.2 平台接入表单

| 平台 | 用户输入 | 浏览器保存 |
|---|---|---|
| 北移 | 无；使用当前登录会话 | 仅现有 `sessionId` |
| 中移商城 | 当前 `wx.10086.cn` Cookie | 不写 localStorage，创建会话后清空输入 |
| 网格通 | 手机号、完整可信入口 URL | 不写 localStorage，创建会话后清空入口 |

切换平台时若已有未完成会话，弹出确认并调用 DELETE 销毁，防止凭据和流程串用。

### 4.3 响应式布局

- 桌面：左侧 280 px 平台/步骤栏，右侧单一工作区。
- 移动：平台控件和步骤条置顶，内容单列，底部动作栏固定但不得遮挡结果。
- 产品事实使用无边框定义列表；可选档位使用单层卡片，不嵌套卡片。
- 控件圆角不超过 8 px；图标按钮使用 Lucide 和工具提示。

## 5. 状态设计

### 5.1 状态转换

| 当前状态 | 事件 | 下一状态 | 失败处理 |
|---|---|---|---|
| 无会话 | 创建 | `INITIALIZED` | 保留输入，展示校验错误 |
| `INITIALIZED` | 准备 | `PRODUCT_READY` | 会话可重试准备；认证失效需重建 |
| `PRODUCT_READY` | 选档 | `SELECTION_READY` | 保留产品，允许重选 |
| `SELECTION_READY` | 发短信 | `SMS_SENT` | 保留选择，恢复发送按钮 |
| `SMS_SENT` | 验证码错误 | `SMS_SENT` | 清空验证码，允许重输 |
| `SMS_SENT` | 最终确认 | `SUBMITTING` | 按结果落最终状态 |
| `SUBMITTING` | 明确受理 | `FINISHED` | 禁止重复提交 |
| `SUBMITTING` | 明确拒绝 | `FAILED` | 禁止同一会话再次确认 |
| `SUBMITTING` | 不确定 | `UNKNOWN` | 禁止重复提交，提示核验 |

北移首次 `compositeCommit` 本质上发生在发送短信之前，但公共层将其封装在 `sendSms` 动作：如果首次提交直接受理，可直接进入 `FINISHED`；如果要求短信，则进入 `SMS_SENT`。

### 5.2 页面恢复

前端保存订购 `sessionId` 只到当前页面内存。刷新页面不会恢复包含商城 Cookie 或网格通 token 的流程，避免在浏览器持久化敏感上下文。后端 GET API用于当前页面操作后的状态同步和短暂网络恢复。

## 6. 数据模型

### 6.1 私有会话

```text
QuickOrderSession
  id: UUID
  platform: north | retail | grid
  businessId: string
  stage: enum
  maskedPhone: string
  product: ProductView?
  selection: SelectionView?
  privateContext: platform-specific object
  smsSentAt: number?
  finalStartedAt: number?
  lastResult: ResultView?
  confirmationId: string?
  createdAt / updatedAt / expiresAt: number
```

### 6.2 产品和选项

```text
ProductView
  name, code, description
  eligible, eligibilityMessage
  options[]
  protocol?
  warnings[]

OptionView
  id, name
  feeText?
  price?
  effectType?
  metadata[]
```

`metadata` 只允许经过白名单的展示字段，不包含 Cookie、token、手机号和上游内部认证信息。

### 6.3 结果

```text
ResultView
  accepted: boolean
  uncertain: boolean
  code: string
  message: string
  orderId?: string
  orderStatus?: string
  retryAllowed: false
  completedAt: ISO string
```

所有最终状态 `retryAllowed` 固定为 false。需要重新办理时必须销毁会话、重新读取实时产品并再次人工确认。

## 7. 平台流程设计

### 7.1 北移

```text
门户登录会话有效
  -> HCLLFFInitData
  -> 展示动态低消、资源和规则
  -> 选择唯一实时资源
  -> 首次 compositeCommit
     |-- 直接受理 -> 结果
     `-- 需要短信 -> sendDXSMS -> checkDxCodeForMT
                                  -> 原 payload compositeCommit -> 结果
```

设计重点：`productShowCode` 和 `plan_fee` 只取初始化响应；短信后二次提交必须使用首次保存的 payload，不在验证码阶段重新拼装。

### 7.2 中移商城

```text
商城 Cookie
  -> userAuth
  -> 页面实例
  -> 实时规格列表
  -> 规格详情 + 协议 + productPreCheck
  -> sendSms
  -> createOrder
```

设计重点：页面产品编码、规格后端 `packageId` 和 `normId` 是三种不同标识；同一验证码需要写入三个兼容字段；协议 `ptId` 来自当次查询。

### 7.3 网格通

```text
可信入口 URL + 手机号
  -> 加载页面会话
  -> 客户校验
  -> 实时档位
  -> 选择 WARE_PLAN_ID
  -> 发送短信，保存挑战号
  -> 校验验证码，保存一次性 token
  -> commitCYDS 普通表单
  -> 解析结果页或 UNKNOWN
```

设计重点：重发短信后挑战号必须覆盖；验证码校验成功后立刻进入提交锁；结果 HTML 没有明确业务成功证据时不能显示成功。

## 8. 确认与防误操作设计

最终确认弹窗固定展示：

| 项目 | 内容 |
|---|---|
| 平台 | 北京移动 / 中移商城 / 网格通 |
| 号码 | 掩码号码 |
| 产品 | 实时产品名和编码 |
| 档位 | 实时档位名 |
| 费用 | 价格、低消或承诺消费原文 |
| 生效 | 上游返回的生效类型或规则摘要 |
| 协议 | 是否已读取并同意 |
| 风险 | 合约期、违约、原套餐影响、结果未知不得重试 |

用户勾选“我确认这是运营商真实订购操作”后，前端生成新的 `confirmationId`。弹窗打开前生成，关闭后作废，避免旧确认被其他选项复用。

## 9. 错误体验设计

- 输入错误：字段下方短提示，不销毁会话。
- 登录失效：明确提示更新北京移动登录或商城 Cookie。
- 资格拒绝：展示上游原意，不默认提供提交按钮。
- 验证码错误：保留短信阶段，清空输入并允许重输。
- 业务明确拒绝：结果区显示代码和提示，隐藏再次确认。
- 结果未知：黄色警告带，显示完成时间和官方查询建议，不出现重试按钮。
- 会话过期：清理页面状态，要求从接入步骤重新开始。

## 10. 部署设计

### 10.1 进程和路由

不新增端口或进程。后端继续监听既有 `PORT`，Nginx/Cloudflare 继续代理同一站点。新增路径均在 `/api/quick-orders` 下，前端构建文件由 Express 提供。

### 10.2 网络要求

运行主机需要访问：

- `https://service.bj.10086.cn`
- `https://wx.10086.cn`
- `https://ysmapp.bj.10086.cn`

不关闭 TLS 校验，不配置全局代理，不允许通过请求参数改变目标主机。

### 10.3 迁移

本版本无数据库迁移。发布顺序：

1. 部署后端和前端同一构建。
2. 健康检查 `/api/health`。
3. 检查 `/api/quick-orders/catalog`。
4. 仅用 mock/测试环境完成页面验收。
5. 分平台安排人工登录和测试号码联调。

## 11. 测试设计

### 11.1 适配器夹具

每个平台至少提供：

- 完整成功链。
- 认证或入口失效。
- 产品/档位为空。
- 资格明确失败。
- 短信发送失败和冷却。
- 验证码错误。
- 最终业务拒绝。
- 最终请求超时、连接重置、格式异常 -> `UNKNOWN`。

### 11.2 页面验收矩阵

| 视口 | 验收 |
|---|---|
| 1440 x 900 | 双栏、弹窗、长协议、结果区无溢出 |
| 1024 x 768 | 工作区可扫描，动作区不遮挡 |
| 390 x 844 | 单列、平台控件可用、长 URL/产品名换行 |
| 360 x 800 | 最长按钮文字和错误码不溢出 |

## 12. 首次真实联调计划

真实联调必须逐个平台单独执行，用户负责手动提供有效登录态或完成登录。每个平台先做到“准备产品”和“发送短信”前暂停，由操作员核对号码、产品、档位和费用；最终验证码和确认由操作员当场输入。

联调后只保存脱敏证据：端点、HTTP 状态、业务码、字段结构、成功/失败语义和订单号格式。不得保存 Cookie、Authorization、验证码、挑战号、一次性 token 或完整手机号。

## 13. 验收标准

- 三个平台从接入到结果均可由同一工作台完成。
- 前后端拒绝非法状态和浏览器注入档位。
- 最终提交锁、幂等和 `UNKNOWN` 规则有自动测试。
- 三个平台协议和加密测试与 HAR/保存源码证据一致。
- 日志抽检无敏感值。
- 前端构建、后端测试和桌面/移动端浏览器验收通过。
- 未获得真实成功样例的平台不会将未知响应判为成功。

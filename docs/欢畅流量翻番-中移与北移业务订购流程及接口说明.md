# 欢畅流量翻番：中移与北移业务订购流程及接口说明

版本：V1.0  
分析日期：2026-07-24  
适用对象：产品、前端、后端、测试、联调与运维人员  
文档性质：基于页面源码与 HAR 实例的接口还原文档

## 1. 文档目的与结论

同一个“欢畅流量翻番”业务存在两套独立订购实现：

- 中移页面位于 `wx.10086.cn/website/businessPlatform`，采用全国新零售商城式通用商品订购链路。页面先查询商品页、规格、协议、优惠和预校验，再发送业务验证码，最后调用通用创建订单接口。
- 北移页面位于 `service.bj.10086.cn/nwt/portal`，采用北京移动省内 BFF 专用活动链路。页面先通过专用初始化接口判断资格并返回动态产品参数，再调用通用组合办理接口；若返回短信二次确认状态，则进入省内短信确认页，校验成功后以原参数再次提交组合办理。

两套页面展示的是同一类合约业务规则，但产品编码体系、认证方式、加密协议、短信接口、提交接口和状态机均不相同，不能只替换域名或产品编码进行复用。

> 证据边界：中移 HAR 的业务报文已依据页面源码完整解密。中移最终提交使用了示例验证码，实测结果为验证码错误，并非成功订购。北移业务报文采用每次页面会话随机生成的 AES 密钥，离线 HAR 不包含该明文密钥；北移字段结构来自同批页面源码，调用顺序和 HTTP 状态来自 HAR。文中明确区分“抓包实证”“源码定义”和“未捕获成功样例”。

## 5. 中移订购完整流程

### 5.1 前置条件

1. 打开页面：`GET /website/businessPlatform/newCustomShopDetail?personalPageId=...`。
2. 浏览器必须保留同域登录 Cookie，并允许 `withCredentials`。
3. 调用 `userAuth` 获取商城业务 Token 和用户上下文。返回 `encVersion=2` 后，后续业务请求切换到新版 AES-256-CBC 加密。
4. 后续请求携带 `Authorization`、`channelid=BUSINESS_H5`、`x-app-version=1.0.2`。样例还携带 `X-Center-Env=1` 和 `Chop-Second-Channel=P00000116110`，两者应使用认证响应值，不能硬编码。

### 5.2 时序步骤

1. 用户认证：`userAuth`。
2. 查询用户策略：`queryPolicy`。
3. 加载个性化商品页：`newProductPersonalPageById`。
4. 并行加载商品关联关系、商户配置和营销机会规则：`queryRelevancy`、`merchant/config`、`ruleNew`。
5. 选择规格后并行查询可用优惠券、关联优惠券：`queryAvailableCoupon`、`queryProdRelatedCoupon`。
6. 查询规格详情：`norm`，得到 `normId`、规格后端编码、预校验类型、业务规则及协议控制字段。
7. 查询业务受理协议：`queryProtocol`，得到 `ptId`。
8. 业务预校验：`productPreCheck`；仅当内层 `status=0` 且 `message=success` 时允许继续。
9. 用户点击获取验证码：`sendSms`，前端启动 60 秒倒计时。
10. 用户输入验证码并确认办理：前端组装 `createOrder` 入参，将同一验证码写入 `password`、`cmgSmsCode`、`verifyCode`，提交订单。
11. 以 `returnCode`、`returnMessage` 和 `data` 判断结果。网络异常与超时不能直接判定失败，应提示“以短信通知为准”并避免自动重复提交。

## 6. 中移接口详细说明

### 6.1 用户认证 `userAuth`

**请求**

- 方法：`POST`
- 路径：`/website/nrapigate/nrauth/auth/encryt/userAuth`
- Content-Type：`application/json; charset=UTF-8`
- 首次请求体：AES-128-CBC/PKCS7 加密后的大写 Hex 字符串。

| 字段 | 类型 | 必填 | 样例 | 说明 |
|---|---|---|---|---|
| `backUrl` | String | 是 | `/website/businessPlatform/newCustomShopDetail?personalPageId=...` | 登录成功后返回的业务页面相对地址 |

**响应公共字段**

| 字段 | 类型 | 说明 |
|---|---|---|
| `returnCode` | String | `0` 表示认证成功 |
| `returnMessage` | String/null | 错误或提示信息 |
| `data.token` | String | 后续 `Authorization` 请求头值 |
| `data.redirectUrl` | String/null | 需要跳转登录或其他认证页面时使用 |
| `data.userInfo.status` | String | 样例 `1`，表示已识别登录用户 |
| `data.userInfo.provinceCode/cityCode` | String | 用户省市；样例均为 `100` |
| `data.userInfo.encVersion` | String | 样例 `2`，决定业务报文使用新版 AES 加密 |
| `data.userInfo.centerFlag` | String | 写入 `X-Center-Env` |
| `data.userInfo.secondChannel` | String | 写入 `Chop-Second-Channel` |
| `data.userInfo.telephone/aesTelNum` | String | 加密后的号码标识，不能当作明文手机号展示 |

## 7. 中移报文加密与公共响应

### 7.1 登录报文

- 算法：AES-128-CBC，PKCS7 Padding。
- 密文编码：Hex，大写。
- 页面源码包含客户端兼容密钥和 IV；文档不建议在新服务端实现中复刻前端静态密钥。最佳方式是由受控浏览器页面或官方 SDK 完成认证。

### 7.2 业务报文（`encVersion=2`）

- 算法：AES-256-CBC，PKCS7 Padding。
- 明文：`JSON.stringify(data)`。
- 密文编码：Base64，传输前将 `+` 替换为 `-`、`/` 替换为 `_`。
- 响应：外层为 `{"body":"<ciphertext>"}`，解密后得到业务 JSON。
- 请求头：`x-app-version=1.0.2`、`Authorization=<AUTH_TOKEN>`、`channelid=BUSINESS_H5`，并按认证结果追加中心环境和二渠道头。

### 7.3 公共响应判定

| 字段/状态 | 含义 | 建议处理 |
|---|---|---|
| `returnCode="0"` | 接口层成功 | 继续检查业务内层状态 |
| `returnCode=401` | 登录态失效 | 清理本地用户态并重新认证 |
| `returnCode=40401` | 网关类错误 | 作为可重试网关异常处理 |
| `ok=true/false` | 页面解密后辅助标记 | 不替代 `returnCode` 和业务状态 |
| HTTP 200 + 非零 `returnCode` | 业务失败 | 展示 `returnMessage`，不可按成功处理 |

## 8. 北移订购完整流程

### 8.1 登录与密钥握手

1. 页面检查 `localStorage.access_token`。无 Token 时调用 `/nwt/sso/touchLogin` 或跳转北京移动登录页；该登录动作在本次业务 HAR 开始前已完成。
2. 调用 `POST /nwt/portal-bff/api/keys/v1.0/get` 获取本次会话使用的服务端公钥材料。
3. 页面随机生成 16 字符 AES 会话密钥 `<SESSION_AES_KEY>`。
4. 页面用服务端公钥加密 AES 密钥，得到 `X-DATA-TOKEN`；后续加密接口均携带该头。
5. 页面维护递增版本号，AES 加密后写入 `X-REPLAY-VERSION`，用于防重放。
6. 每次页面重新加载或进入短信确认页均可能重新握手，不能跨页面复用旧的 `X-DATA-TOKEN`、重放版本或密文。

### 8.2 业务时序步骤

1. 进入 `enjoyTrafficDoubling`，完成 OAuth 登录态和密钥握手。
2. 调用 `HCLLFFInitData` 查询资格、承诺消费、流量档位、违约金额和动态产品展示编码。
3. `resultCode=00`：展示可办理页；`11`：跳转已办理页；其他值：跳转不满足页。
4. 用户点击办理，页面组装组合办理参数并调用第一次 `compositeCommit`。
5. 若返回特殊状态 `code=need_sms_check` 且 `data.pageType=success_new`，请求拦截器保存确认数据并跳转 `mtSMSValidationV1`。
6. 短信确认页从本地存储恢复原始 `commitData` 和服务端 `commitResultData`，显示掩码号码、产品名称、确认说明和生效时间。
7. 用户点击获取验证码：根据 `smsType` 调用 `sendDXSMS` 或 V2。本次源码与 HAR 走 `need_sms_check_v1` / `sendDXSMS`。
8. 用户输入 6 位验证码，调用 `checkDxCodeForMT`。
9. 仅当 `data.result=00000` 时，以第一次完全相同的业务参数再次调用 `compositeCommit`。
10. 根据最终 `data.resType` 或 `showBLJG` 后续结果进入成功/失败结果页。最终提交必须做单次点击锁，避免重复办理。

### 8.3 北移接口清单

| 序号 | 接口 | 级别 | 作用 | 证据状态 |
|---|---|---|---|---|
| 0 | `POST /nwt/sso/touchLogin` | 前置必需 | 获取/刷新 OAuth Token | 源码定义，本次 HAR 未捕获 |
| 1 | `POST /portal-bff/api/keys/v1.0/get` | 必需 | 初始化会话加密材料 | HAR 捕获 4 次 |
| 2 | `POST /portal-bff/api/mPersonBusi/v1.0/HCLLFFInitData` | 必需 | 查询资格和动态产品参数 | HAR 捕获，源码定义字段 |
| 3 | `POST /portal-bff/api/sjyw/biz/core/v1.0/compositeCommit` | 必需 | 首次提交并触发短信确认；校验后再次提交 | HAR 捕获首次提交，源码定义二次提交 |
| 4 | `GET /portal-bff/api/mtsms/v1.0/sendDXSMS` | 必需 | 发送确认验证码 | HAR 捕获 |
| 5 | `GET /portal-bff/api/mtsms/v1.0/checkDxCodeForMT` | 必需 | 校验确认验证码 | HAR 捕获 |
| 6 | `GET /portal-bff/common/pulic/v1.0/getChannelSource` | 页面辅助 | 获取渠道来源参数 | HAR 明文响应 |
| 7 | `GET /portal-bff/api/needLoginPublic/v1.0/getJtchannel` | 页面辅助 | 获取集团/渠道参数 | HAR 捕获，业务订购不直接依赖 |

## 9. 北移接口详细说明

### 9.1 会话公钥接口 `keys/v1.0/get`

**请求特征**

- 方法：`POST`
- 头：`Authorization: Bearer <ACCESS_TOKEN>`
- 无业务请求体。
- 响应用于建立当前页面会话的加密上下文，不是产品公钥或长期配置。

**实现要求**

| 项目 | 要求 |
|---|---|
| AES 密钥 | 每次握手随机生成 16 字符，不能固定或落日志 |
| `X-DATA-TOKEN` | 用接口返回的服务端公钥封装 AES 密钥；随当前加密会话使用 |
| `X-REPLAY-VERSION` | 以递增计数生成后再加密；不能重用旧值 |
| 页面跳转 | 进入短信确认页后应重新完成握手；HAR 显示两组不同 `X-DATA-TOKEN` |
| `XEbtxIBt` | HAR 中出现的动态查询参数，属于网关/防护层注入值，不是业务入参，禁止硬编码 |

### 9.2 初始化资格 `HCLLFFInitData`

**请求**

- `POST /nwt/portal-bff/api/mPersonBusi/v1.0/HCLLFFInitData`
- 业务逻辑无显式入参；用户由 Bearer Token 和服务端会话识别。
- 需要 `Authorization`、`X-DATA-TOKEN`、`X-REPLAY-VERSION`、`traceId`。

**响应公共外层**

```json
{
  "success": true,
  "code": "bizSuccess",
  "message": "业务操作成功",
  "causedBy": "",
  "data": {},
  "busiToken": null
}
```

**`data` 字段**

| 字段 | 类型 | 业务含义 | 页面处理 |
|---|---|---|---|
| `resultCode` | String | 资格/状态码 | `00` 可办理；`11` 已办理；其他不满足 |
| `plan_fee` | String/Number | 用户动态承诺消费金额 | 页面展示；拼入 `mtOtherParams=1-${plan_fee}` |
| `productCode` | String | 动态产品展示编码 | 首次/二次组合办理的 `productShowCode` |
| `productDesc` | String | 以 `|` 分隔的动态说明 | 第 1 段为赠送流量数；第 2 段为退订合约款/违约金额 |
| `productCrtDate` | String | 已办理业务创建日期 | `resultCode=11` 时传到已办理结果页 |

**状态机**

| `resultCode` | 页面动作 | 必须保存的字段 |
|---|---|---|
| `00` | 展示办理按钮与业务规则 | `plan_fee`, `productCode`, `productDesc` |
| `11` | 跳转 `/trafficDoublingProcessed` | `productCrtDate`, `plan_fee`, 流量数 |
| 其他/空 | 跳转 `/trafficDoublingDissatisfied` | 可记录服务端原始码供排障 |

### 9.3 组合办理 `compositeCommit`

**首次与二次提交使用相同逻辑明文**

```json
{
  "common": {
    "operType": "commitProductNew"
  },
  "body": {
    "content": {
      "packageId": "55412",
      "packageCode": "HCLLFF26",
      "productShowCode": "<HCLLFFInitData.data.productCode>",
      "pitemShowCode": "KT",
      "mtOtherParams": "1-<HCLLFFInitData.data.plan_fee>"
    }
  }
}
```

| 字段 | 类型 | 必填 | 来源/说明 |
|---|---|---|---|
| `common.operType` | String | 是 | 固定 `commitProductNew`，表示新产品办理 |
| `body.content.packageId` | String | 是 | 页面常量 `55412` |
| `body.content.packageCode` | String | 是 | 页面常量 `HCLLFF26` |
| `body.content.productShowCode` | String | 是 | 初始化响应 `data.productCode`，不能写死 |
| `body.content.pitemShowCode` | String | 是 | 固定 `KT`，开通产品项 |
| `body.content.mtOtherParams` | String | 是 | `1-${plan_fee}`；短信确认页也依赖此值替换描述占位符 |

**首次响应的短信确认分支**

| 字段/值 | 含义 | 页面动作 |
|---|---|---|
| `code=need_sms_check` | 需要短信二次确认 | 保存 `data` 为 `commitResultData` |
| `data.pageType=success_new` | 使用新版短信确认页 | 跳转 `mtSMSValidationV1` |
| `data.productItemName` | 待办理产品名称 | 确认页展示 |
| `data.productItemDesc` | 待确认产品说明，可能含 `xx` 占位符 | 使用 `mtOtherParams` 替换后展示 |
| `data.busiTime` | 生效时间/规则 | 确认页展示 |
| `data.typeKey` | 短信产品键 | 发送和校验验证码的 `productKey` |
| `data.smsType` | 短信接口版本 | `need_sms_check_v1` 走 `sendDXSMS`；v2 走 V2 接口 |

**最终响应**

源码读取 `data.resType`，并在 `resType=showbljg` 时继续请求结果展示接口。此次 HAR 没有捕获验证码通过后的第二次 `compositeCommit`，因此没有可验证的最终成功 JSON。联调时应记录脱敏后的 `code/message/data.resType` 和业务受理流水号，并补充到接口契约。

### 9.4 发送验证码 `sendDXSMS`

**源码逻辑参数**

```json
{
  "productKey": "<commitResultData.typeKey>",
  "mtOtherParams": "1-<plan_fee>"
```

- 通用请求层将参数序列化并 AES 加密为查询参数 `p`；HAR 中又出现网关改写后的 `XEbtxIBt`，业务实现不应直接构造 HAR 的最终 URL。

| `data.result` | 非 `00000` | 提示“您输入的验证码有误，请重新输入” |

验证码为空时前端不发请求，直接提示“请输入短信验证码”。输入框限制为 6 位数字。

## 10. 北移加密、请求头与响应状态

### 10.1 业务报文加密

| 项目 | 实现 |
|---|---|
| 明文 | JSON 字符串或序列化查询参数 |
| 算法 | AES-ECB，PKCS7 Padding |
| 密钥 | 当前页面握手生成的 16 字符随机密钥 |
| POST 数据 | `encodeURIComponent(AES(JSON.stringify(data)))` |
| GET 参数 | 先序列化键值，再 AES 加密到 `p`；实际线上 URL 还可能被网关改写 |
| 响应 | 使用同一会话 AES 密钥解密，再按 JSON 解析；大整数按字符串保留 |

### 10.2 核心请求头

| 请求头 | 必需性 | 说明 |
|---|---|---|
| `Authorization: Bearer <ACCESS_TOKEN>` | 必需 | OAuth 登录令牌；过期后重新登录/刷新 |
| `X-DATA-TOKEN: <X_DATA_TOKEN>` | 加密接口必需 | RSA 封装后的当前会话 AES 密钥 |
| `X-REPLAY-VERSION` | 加密接口必需 | 加密后的递增版本，防止重放 |
| `traceId` | 必需/建议 | UUID 去连字符，用于链路追踪 |
| `Content-Type: application/json;charset=UTF-8` | POST 必需 | BFF 默认内容类型 |
| Cookie | 浏览器链路需要 | 同域会话、负载均衡和登录上下文；禁止复制他人 HAR Cookie |

### 10.3 公共响应与特殊状态

| `code` / 条件 | 含义 | 处理 |
|---|---|---|
| `success=true` 且 `code=bizSuccess` | 普通成功 | 返回业务 `data` |
| `need_sms_check` | 需要短信确认 | 保存确认数据并跳转对应短信页 |
| `smsVerification` | 通用短信验证状态 | 跳转短信验证页 |
| `kdtgSmsVerification` | 特定活动短信验证 | 保存数据并跳转专用页 |
| `portalGlobalErr` | 门户全局错误 | 写入错误信息并跳转错误页 |
| `terminalErr` / `terminalSubmitOrderErr` | 终端业务错误 | 跳转相应错误页 |
| `ykdGlobalErr` | 宽带全局错误 | 跳转宽带错误提示页 |

### 11.2 幂等与重复提交

| 风险 | 建议 |
|---|---|
| 用户多次点击确认 | 前端点击后立即锁定；后端按用户、业务编码、挑战号、短时间窗口做幂等 |
| 网络超时但后台已受理 | 不自动重试创建订单；先查询结果或等待业务短信 |
| 北移二次 `compositeCommit` | 只允许验证码成功分支触发一次；保留原始参数的不可变副本 |
| HAR/密文重放 | 所有 Token、Cookie、AES 会话、验证码、时间戳和重放版本均需实时生成 |
| 同一用户已办理 | 中移依赖预校验/订单响应；北移 `resultCode=11` 直接转已办理页 |

### 11.3 服务端代理边界

- 推荐采用“受控浏览器会话 + 服务端会话引用”模式，不将用户 Cookie、Token 或 AES 密钥暴露给普通前端日志。
- 不建议把 HAR 中的完整请求头复制为固定模板。浏览器版本头、WAF 参数、负载均衡 Cookie、埋点 Cookie均不是稳定业务契约。
- 若必须服务端直连，应先获得平台正式接口授权、密钥协议和幂等规范；页面源码中的客户端加密只说明现状，不等于服务端开放接口承诺。
- 日志只记录接口名、平台、脱敏用户标识、业务编码、业务状态码、耗时、traceId；禁止记录短信验证码、Authorization、Cookie、`X-DATA-TOKEN` 或明文 AES 密钥。

## 12. 联调与测试用例

| 用例 | 中移预期 | 北移预期 |
|---|---|---|
| 未登录进入 | `userAuth` 返回跳转/未登录态 | 进入 `touchLogin` 或登录页 |
| 正常加载 | 页面、规格、协议和预校验均成功 | `resultCode=00`，展示动态承诺金额与流量 |
| 已办理 | 预校验或订单接口返回已订提示 | `resultCode=11`，跳转已办理页 |
| 不满足资格 | 预校验内层非成功 | 初始化其他结果码，跳转不满足页 |
| 短信发送成功 | 外层 `0` 且 `data.status=0`，60 秒倒计时 | `sendDXSMS` 成功，60 秒倒计时 |
| 验证码错误 | `createOrder` 返回非零，如 `SMS_9999` | `checkDxCodeForMT.data.result != 00000` |
| 验证码正确 | 创建订单返回业务成功和订单号 | 校验 `00000` 后二次 `compositeCommit` |
| 接口超时 | 提示以短信为准，不自动重提 | 保留页面状态，禁止重复二次提交 |
| Token 过期 | 清理用户态并重新 `userAuth` | 刷新或重新 OAuth 登录，重新密钥握手 |
| 旧密文重放 | 应失败或被拒绝 | `X-REPLAY-VERSION`/会话 Token 拒绝旧请求 |
| 协议未加载 | 禁止提交或重新查询协议 | 首次组合办理负责返回确认内容 |
| 优惠券为空 | 按无券办理 | 不涉及商城优惠券链路 |

## 13. 上线验收清单

- 已按平台隔离认证、加密、短信和订购适配器。
- 中移严格区分页面 `productCode` 与规格 `data.productCode/packageId`。
- 北移 `productShowCode`、`plan_fee`、`productDesc` 全部使用初始化返回值。
- 预校验和资格判断同时检查接口外层成功与内层业务状态。
- HTTP 200 不作为订购成功条件。
- 短信验证码只在用户当次会话内使用，不落库、不落日志。
- 北移进入短信页后重新握手，不复用旧 `X-DATA-TOKEN`。
- 北移验证码成功后只执行一次二次 `compositeCommit`。
- 对网络超时设置“结果未知”状态，禁止自动重复下单。
- 保存脱敏订单流水、业务状态码、traceId、调用耗时和平台标识。
- 已覆盖已办理、不满足、验证码错误、Token 过期、重复点击和超时场景。
- 成功联调后补录两平台真实成功响应结构和可查询的订单状态接口。

## 14. 已知限制与待补证项

1. 中移 HAR 的最终订单响应是验证码错误，未提供成功订单号样例；成功结构中 `data.orderNumber`、`data.successTime` 来自源码读取逻辑。
2. 北移 HAR 未包含会话随机 AES 明文密钥，无法离线解密动态业务值；字段名、状态分支和入参来自同批线上页面源码。
3. 北移 HAR 在验证码校验后没有出现第二次 `compositeCommit`，说明本次样例未完成最终成功提交或校验未通过。
4. 两平台页面接口均可能随版本升级调整。生产实现应以正式开放接口契约为准，并在每次页面版本变更后回归字段映射、加密和状态码。
5. 当前材料不包含订单结果查询/退订接口；本文范围仅为业务订购。若需要完整生命周期，还应补充已订状态查询、订单结果查询、退订预校验、短信退订和最终退订接口。

# 山西移动 WAP 产品功能说明

版本 1.0　分析基准 2026年9月20日　适用读者 产品经理 业务负责人 研发与测试

山西移动 WAP 是由账户认证、通信服务查询、业务办理、充值支付、金币与权益、企业及家庭服务组成的触屏营业厅。当前可完整阅读的业务页面为全球通 5G-A 加速权益；其余能力主要由路由和接口封装证明存在，具体在售状态、资费与可办条件应由业务配置和服务端结果确定。

## 1 产品范围与证据等级

本次分析对象为《山西移动WAP.zip》和《山西移动登录.har》。ZIP 含 30 个文件，属于已构建的浏览器资源；主应用采用 Vue、Vue Router、Vuex 与 Axios 的组织方式。发现 92 条路由配置，分包映射声明 90 个异步包，但实际仅包含 0 和 14，另有主包、依赖包与运行时包。88 个异步包不在材料中，不能把路由名称等同于完整页面实现。

接口清单按材料中的不同地址计数，共 307 项：283 项具有请求声明或直接调用，22 项仅在字符串或公共处理名单中引用，2 项仅在 HAR 出现。相对地址按 act 页面上下文解析；market 的登录接口保留独立地址。它们并非 307 个已验证可用的服务。

| 等级 | 含义 | 可支持的结论 |
| --- | --- | --- |
| A | 抓包可解析业务结果 | 获取 RSA 公钥、广告配置接口返回业务成功 |
| B | 抓包可见但业务体加密 | 证实请求方法、地址、外层字段和 HTTP 状态 |
| C | 源码实现或请求封装 | 证实前端契约与处理逻辑，不保证服务端当前行为 |
| D | 路由或字符串引用 | 功能线索，参数、权限、有效性仍需补证 |
| 建议 | 本方案提出的产品或工程要求 | 不代表原系统已经实现 |

HAR 共 28 条请求，8 条为业务 API，20 条为页面或静态资源，均返回 HTTP 200。6 条 API 使用无法从当前材料恢复明文密钥的 AES 报文；另 2 条可读出业务成功。未观察到订购提交、退订或支付的真实请求。

## 3 用户与使用场景

普通用户通过浏览器、微信或移动 APP 容器访问营业厅，查看账户资料并办理符合资格的业务。全球通用户进入专属权益页领取可办权益；企业、家庭与物联网用户使用各自场景的查询及订单入口。源码包含 GOLD_MANAGE_LOGIN、ASSIST_MANAGE_LOGIN、SMS_MANAGE_LOGIN 等类型，但前端枚举不能证明服务端角色权限模型，应单独核定管理权限。

产品应在展示层区分游客、已登录用户、资格不满足、默认已享有、已办理、办理中、成功、失败及结果待确认。账户身份和资格来自服务端，页面按钮是否可见不能替代业务授权。

## 4 登录与会话流程

业务页首先调用登录态检查。以 5G-A 为例，公共模块以 SSO_LOGIN 类型检查；成功后读取 phone_no 并启动资格查询。无有效登录态时可加载统一认证 SDK 尝试令牌登录，随后进入 market 的 loginSim 页面，携带编码后的 back 地址和 busiType。接口返回 999999 时，公共响应处理清空用户状态并引导重新登录。

HAR 的 startedDateTime 表明先发送 market 短信请求，再发送 market 登录请求，随后进入 act 页面。HAR 数组本身未按时间排列，不能把数组第 26、27 项误读成先登录后发短信。抓包未能证明短信发送或登录业务成功，实际请求明文、登录方式及验证码字段仍待登录页实现补齐。

已有源码明确实现另一条令牌登录契约：pubInfo 中包含 loginSourceCode、loginType、token、userinformation 和 busiType，busiInfo 承载业务场景信息。它属于 act 侧公共登录逻辑，不可直接当作 market 短信登录请求的字段定义。

## 5 全球通 5G A 加速权益

### 5.1 产品规则

页面文案规定：全球通卓越钻石卡、钻石卡、白金卡客户直接享有；普卡、银卡、金卡客户可免费办理。页面显示费用 0 元，使用有效期与当前全球通身份有效期一致；权益不可共享、不可转赠，需支持 5G-A 的终端并接入 5G 网络。实际生效以开通成功短信为准。这是材料版本中的产品规则，不是对未来资费或在售状态的承诺。

资格成功后从顶层 gBrandLevel 或 data.gBrandLevel 取值。代码将 08、04、03 视为默认享有；02、01、00 允许展示可办卡片。数字编码与具体卡名不宜在缺少字典时额外推定。

### 5.2 办理链路

1. 初始化登录检查并取得手机号，在页面展示脱敏号码。
2. 调用 qqt5ga/qryUserQualification，按业务码和会员等级判断可办性。
3. 用户打开办理确认弹窗，展示业务名称、0 元资费和生效说明。
4. 初始化业务短信组件，先查询是否敏感业务，再发送相应验证码。
5. 校验成功后写入 busiSms-uuid 和 busiSms-type Cookie，触发页面验证完成事件。
6. 用户提交；页面调用 qqt5ga/submitPrcOrder，公共拦截器补入短信凭据及页面名称后加密发送。
7. retCode 数值为 0 时展示成功；其他业务码或异常展示失败。源码中失败也会将 hasProcessed 置为 true，本次页面状态不会直接允许再次提交。

| 参数或状态 | 页面值或行为 |
| --- | --- |
| busiType | QQT5GA_SMS |
| sendType | 字符串 2 |
| prcId | BCAT5075 |
| prodName | 5GA加速权益 |
| busiName | 全球通5GA加速权益 |
| effDate | 立即生效，最终提示仍以成功短信为准 |
| 提交前置状态 | checkBusiSms=true 且未处理、未提交中 |
| 重复点击 | isSubmitting 在请求期间阻止重复调用 |
| 后端幂等 | 未有证据，不可把按钮锁等同于后端幂等 |

### 5.3 资格与结果提示

| 业务码 | 源码定义的界面处理 |
| --- | --- |
| 0000 | 进入资格数据与等级判断 |
| 900004 | 暂无可领取权益 |
| 900005 | 默认享有，无需办理 |
| 900006 | 已领取，无需再次办理 |
| 900010 | 资格已过期 |
| 999999 | 公共层按未登录处理 |
| 其他码或网络异常 | 显示业务消息或查询失败，不能推断订购成功 |

### 5.4 短信交互

普通模式输入 6 位数字，自动触发校验，重发倒计时 60 秒。敏感模式从服务端取得 pos1、pos2、val1、val2，在 8 位验证码中固定两个位置，由用户补齐另 6 位；校验时发送完整 8 位和 isSensitive=Y。敏感分支维护 60 秒倒计时、最多 3 次成功发送计数及组件代次校验，避免已关闭弹窗的异步结果污染新状态。次数和倒计时均为前端行为，不能推断服务端限频或验证码有效期。

## 6 查询 订购 退订与支付的通用要求

查询类能力应先判定登录与角色，再显示列表、空态或可解释的业务错误；金额、流量单位、账期及币种均应由明确字段字典支持。当前大部分接口仅有统一请求封装，不能补写不存在的金额单位、分页参数或返回数组。

办理类能力应依次完成产品与资费展示、资格校验、必要的短信验证、用户确认、单次提交和结果查询。此流程是实施建议；只有 5G-A 的页面链路已经在代码中逐步确认。取消订单、业务退订和支付不能共用一个笼统的“撤销”，应分别展示生效时间、费用影响和可逆性。

支付成功应以服务端订单状态为准。前端跳转到结果页只说明完成导航；超时、断网或用户离开页面应进入结果待确认状态。建议先查询订单，再决定恢复操作，不自动重放创建订单、扣费、兑换或退订请求。

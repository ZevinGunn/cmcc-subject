# 山西移动 WAP 认证加密与实施方案

版本 1.0　分析基准 2026年9月20日　适用读者 技术负责人 安全评审 研发与测试

当前前端同时保留统一 AES 报文协议和旧版 DES 字段或业务报文协议。desRest 是历史配置名，实际启用 AES-128-CBC、RSA 公钥加密和 HMAC-SHA256。实现集成时首先保留已有协议边界，再通过明确契约补齐登录、短信、订购和结果查询；不可将不同协议或 act 与 market 的地址混成一个通用接口。

## 1 架构与模块关系

浏览器页面由 Vue 路由和分包加载业务组件，Vuex 保存用户及公钥等状态。业务组件调用统一 API 类；Axios 请求拦截器添加业务上下文、短信凭据与采集头，对 desRest 请求执行加密；响应拦截器解密、清理短信凭据、处理失效登录态与统一提示。应用同时依赖浏览器 Cookie、本地存储、统一认证 SDK 和 YWKJ 容器能力。

页面组件 → 业务接口封装 → 公共字段补入 → 密钥获取与报文加密 → 浏览器同源请求 → 响应解密 → retCode 处理 → 页面状态更新。

证据为 APP oHCY 模块 6430 至 6484、w//H 模块 6757 起、请求与响应拦截器 9720 至 9786，以及 COMMON 的认证与短信组件。前端资产无法证明服务端内部架构、数据库、权限过滤与支付结算实现。

## 2 统一加密协议

### 2.1 每请求密钥与关联标识

oHCY.c() 生成由 A-Z、a-z、0-9 组成的 16 字符字符串 K，按 UTF-8 解释为 16 字节 AES 密钥。字符选择使用 Math.random；因此不能把该生成器描述为密码学安全随机源，也不能仅凭“16 字节”断言实际随机熵达到 128 位。

同时生成 s1，内容由毫秒时间戳与随机数字组合而成，在内存映射 r[s1] 中保存 K。Axios 配置字段名称是 s1Radom，保留原拼写。s1 用于把响应关联到本次请求的 K，当前代码不把它作为协议请求头。模块中未看到响应后删除 r[s1] 的逻辑，长会话的内存生命周期应复核。

### 2.2 AES 负载

对完成公共字段注入后的业务对象执行 JSON.stringify，使用 UTF-8 编码。CryptoJS 生成 16 字节 IV，采用 AES-CBC 与 PKCS7 填充，得到密文字节 C。

encryptInStr = hex(IV) + hex(C)

前 32 个十六进制字符代表 IV；其后才是密文。线上格式没有 Salted__ 包装，也不是整体 Base64。响应 encryptOutStr 使用相同拼接布局，前端以原请求保存的 K 解密。不要把 K 本身按十六进制解析，也不要将随机 IV 固定为常量。

### 2.3 RSA 密钥封装

getRsaPubKey 获取十六进制 DER 公钥，Vuex 缓存公钥并维护并发等待队列。HAR 中公钥为 RSA 2048 位、指数 65537。JSEncrypt.encrypt 对 K 执行 RSAES-PKCS1-v1_5 加密，源码 vendor 47275 起可见 00 02、非零随机填充及 00 分隔字节。它不是 OAEP，也不是服务端签名。

JSEncrypt 返回 Base64，应用再解码为字节并转换为十六进制写入 E-A-K。样本长度为 512 个十六进制字符，即 256 字节。实际兼容实现应按公钥模数长度确定输出，不应将该样本长度当成永久常量。

### 2.4 HMAC 与时间戳

T 为十进制毫秒时间戳。签名输入是 T 的字符串与完整 encryptInStr 直接拼接，无分隔符；不是原始 JSON，也不包含 URL。HMAC 的密钥为同一字符串 K 的 UTF-8 字节。

E-S-K = hex(HMAC-SHA256(K, UTF8(T + encryptInStr)))

E-T-K = T，E-A-K = hex(RSA_PKCS1_v1_5(publicKey, UTF8(K)))。

HMAC 提供共享密钥下的报文认证，不能描述为不可抵赖数字签名。客户端代码没有证明服务端检查时间窗、随机数或重复请求；“有时间戳”不等于已经防重放，也不等于订购幂等。

### 2.5 解密分支

secretOutId 为字符串 -1 时，前端将 encryptOutStr 当作 JSON 字符串直接解析。其他情况取本次请求 e.config.s1Radom 对应的 K，将前 32 字符解析为 IV，剩余解析为密文，AES-CBC 解密及去填充后解析 JSON。此版本客户端未展示响应 HMAC 验证；不能把请求 HMAC 自动推定为响应也有独立完整性验证。

### 2.6 可实现的协议伪代码

```text
P = JSON.stringify(业务字段和公共补入字段)
K = 16 字符临时密钥
IV = 16 字节随机数
S = hex(IV) + hex(AES_CBC_PKCS7(UTF8(P), UTF8(K), IV))
T = 当前毫秒时间戳的十进制字符串
headers.E_A_K = hex(RSA_PKCS1_v1_5(公钥, UTF8(K)))
headers.E_T_K = T
headers.E_S_K = hex(HMAC_SHA256(UTF8(K), UTF8(T + S)))
body = {encryptInStr: S}
按请求关联保存 K，收到响应后解密并释放
```

伪代码中的 E_A_K 等名称仅用于便于阅读；真实 HTTP 头为 E-A-K、E-T-K、E-S-K。建议实现使用密码学安全随机源生成 K；兼容性须由协议测试证实，不能单方面把 CBC、RSA 填充或字段名称换成新格式。

## 3 旧版 DES 与其他编码

### 3.1 广告接口

businessTree/adInfoQry 在调用处独立执行 DES-ECB、PKCS7；加密结果为 Base64，装入 encryptStr，secretid 为空。响应 eStr 以 Base64 解码再 DES 解密。源码使用公开在前端的固定字符串作为原始密钥材料，CryptoJS 的 DES 密钥调度使用前 8 字节。本次已在本地复现并解出 HAR 请求 {"appId":"115"} 及返回业务码 0000。

固定密钥属于前端可见协议常量，不能当作服务器秘密或安全边界。本交付不复制常量到正文，准确位置为 APP 2401 和 2413；可从用户原始材料复核。即便材料含较长密钥字符串，也不能误称为 TripleDES。

### 3.2 充值字段及工具方法

APP 5085 起的 encryptByDES 与 6022 起的公共 encryptByDES、encryptByDESRemove 均使用 DES-ECB、PKCS7 和 Base64。充值代码对 phoneNo 与 payWay 采用不同的固定密钥材料，还传递 tradeId、returnUrl、orderId 等。它们是特定支付跳转数据的字段级处理，不能替换统一 AES 请求加密。支付网关完整地址与服务端契约仍需对应业务页补齐。

### 3.3 编码与外部依赖

Base64、十六进制、URL encodeURIComponent、HAR content.encoding=base64 是不同层的编码，不是独立加密算法。HAR 的响应 text 应先按 encoding 解码，再识别 JSON 外层，再处理业务密文。HAR 的 postData.text 才是实际请求主体；其 params 字段出现将 JSON 文本当作参数名的导出结果，不宜拿来重建请求。

在已追踪业务链路中没有发现 SM2、SM3、SM4 的调用证据。依赖包中出现某种算法的实现不代表业务使用它。混淆脚本和 SDK 的内部协议未完整还原，不宣称已经覆盖其中所有动态算法。

## 4 会话与身份边界

HAR 可见 jsession_id_4_boss、ph、ph2、client_cookie 以及不透明和统计类 Cookie；不能仅据名称判断哪一个充分构成登录态。源码还将 phoneNo、userInfo、uuid 等写入 Vuex 或 localStorage。会话身份由服务端判断，页面显示手机号和保存用户信息都不能单独证明已认证。

短信凭据 Cookie 由 j2NP 写入，期限计算为当前时间加 77,760,000 毫秒，即 21.6 小时，未在该函数中设置 path、Secure、SameSite。这个浏览器保存期限不是验证码或服务端凭据的有效期。公共拦截器读取短信凭据后仅对 13 个指定办理地址补入 uuid、busiType，并在 HTTP 成功响应处理阶段清空。跨页面、并发办理以及同名 Cookie 的作用域应专项验证。

统一认证、业务短信确认与反自动化环境校验是三个不同层次。即使能构造 AES 报文，也不能推导出有权操作他人号码、绕过验证码或跳过资格检查。集成应使用服务方支持的认证和业务授权流程。

## 5 已完成验证与可复现证据

| 检查 | 方法 | 结果及边界 |
| --- | --- | --- |
| 来源完整性 | 对两份输入计算 SHA-256 | 哈希写入证据索引，不改原文件 |
| 接口与路由 | 提取调用、名单、路由并与 HAR 合并 | 307 接口项，92 路由，保留证据等级 |
| RSA 公钥 | 对 HAR 明文公钥做 DER 解析 | 2048 位，指数 65537 |
| AES | 隔离执行源码加密模块，使用独立 Python 解密 | 合成测试通过 |
| HMAC | 源码生成摘要，独立 Python 重算 | 完全一致 |
| RSA 填充 | 合成密钥对，源码加密后独立解密 | PKCS1 v1.5 测试通过 |
| 响应关联 | 源码生成临时 K 并加解密回环 | 合成测试通过 |
| 旧版广告 DES | 对 HAR 的请求和响应本地解密 | 请求 appId=115，响应业务成功 |
| 登录与订单 | 不向线上发送请求 | 未验证登录业务结果或真实订购 |

生产 AES 抓包无法从目前保存的数据直接解密：浏览器只把 K 的 RSA 密文上传，公钥不具备解密能力，HAR 也未保存运行时映射 r。离线合成协议验证证明对算法和编码的理解一致，不证明每条线上业务请求的明文或业务成功。

## 6 实施方案

### 6.1 交付模块

建议分成协议适配、会话管理、业务适配、结果核查和审计五个模块。协议适配负责序列化、RSA 公钥、AES、HMAC 与脱敏错误；会话模块隔离用户与渠道身份；业务适配按登录、查询、短信、订购、支付分别管理 schema；结果核查管理办理中和结果未知状态；审计仅保留必要业务编号、脱敏账号、错误码及时间。

协议实现应从已离线验证的核心链路开始，不直接为 307 项全部生成可调用 SDK。先完成一个登录场景、一个只读查询及 5G-A 闭环，取得正式契约后再逐业务域扩展。这能减少将历史或仅引用接口误当成现行能力的维护成本。

### 6.2 数据和状态设计

建议保存用户会话引用、渠道、业务类型、产品标识、操作意图、短信验证状态、提交时间、服务端交易号及最终结果。临时 AES 密钥只保存在请求生命周期中，不写日志和持久化数据库。验证码及完整 Cookie 不进入审计表。日志保留期和访问权限由部署环境的业务与数据要求确认，当前不指定未经确认的天数。

建议的写操作状态为待确认、验证中、可提交、提交中、结果未知、成功、失败。网络超时转为结果未知；有状态查询能力时先核查，再决定是否恢复操作。缺少服务端去重或状态查询契约时，不做自动重试。取消订单和退订由独立状态机处理。

### 6.3 阶段与验收关口

| 阶段 | 工作 | 完成条件 |
| --- | --- | --- |
| 契约补全 | 获取缺失分包、字段字典、业务错误码与订单查询能力 | 核心链路无关键字段猜测 |
| 离线适配 | 实现编码、加密、签名、解密和请求关联 | 固定测试向量及并发隔离通过 |
| 只读联调 | 验证登录、失效、资格与查询 | 脱敏成功失败样本可复核 |
| 写业务联调 | 验证验证码、单次提交、重复提交、结果未知与核查 | 受控账号下业务结果一致 |
| 发布与运维 | 配置隔离、监控、日志脱敏、功能开关和回滚 | 能停止新办理且保留待核查任务 |

当前缺少服务方文档、测试环境与完整分包，无法可靠给出固定工期或承诺成本。可先按上述验收关口形成排期，再由接口可得性、认证方式、业务数量及测试账号条件估算。

## 7 风险与改进优先级

| 优先级 | 已见证据或待验证问题 | 建议措施 |
| --- | --- | --- |
| 高 | 请求 K 使用 Math.random；DES 固定材料前端可见 | 兼容条件下用安全随机源；旧协议通过服务端版本化迁移 |
| 高 | 未见订单幂等及结果核查契约 | 上线前确认去重键、交易号和查询，禁止盲重试 |
| 高 | 缺少 market 登录字段及成功失败明文 | 补齐登录资源与受控样本，不猜测认证参数 |
| 高 | 敏感查询异常时前端转普通短信模式 | 验证服务端独立强制业务验证等级 |
| 高 | 充值金额判断使用 10 <= x < 10000 的 JavaScript 链式比较，不能有效约束范围 | 改为两个显式比较并验证整数和上限；核对服务端金额校验，不能据此前端缺陷推断可异常扣费 |
| 中 | 短信凭据由脚本 Cookie 共享，响应后即清空 | 验证并发与作用域；按业务意图隔离，最小生命周期 |
| 中 | 前端用户信息和令牌日志可被页面脚本读取 | 减少本地保存和敏感 console，限制脚本来源 |
| 中 | 公钥队列及部分认证 catch 只打印错误 | 明确超时、失败释放和可重试边界，避免流程悬挂 |
| 中 | 公共网络错误分支可能返回 undefined | 调用方覆盖无响应对象情形，统一失败契约 |
| 中 | 5G-A 失败将 hasProcessed 置 true | 产品定义查询结果或恢复路径，避免用户被困在失败态 |
| 中 | 88 个异步分包缺失，运营和历史功能状态不明 | 按当前在售业务补齐源码，版本化冻结接口清单 |

以上是对可见前端的风险评估，不是对服务端存在可利用漏洞的认定。认证、权限、限流、支付安全及实际可利用性均需服务端证据与授权测试。

## 8 测试方案

| 类别 | 必测情况 |
| --- | --- |
| 协议 | 中文和空对象、16 字节边界、随机 IV、错误填充、非法 JSON、RSA 公钥失败、签名字段篡改 |
| 并发 | 多请求 K 不串用、公钥单次获取、不同账号会话隔离、短信并行办理 |
| 登录 | 失效、退出、回跳编码、SSO 与管理场景、微信与浏览器来源 |
| 验证码 | 前导零、6 位与 8 位、固定位置非法、重发、关闭重开、过期、频次、旧响应返回 |
| 资格 | 0000 与各拒绝码、会员等级缺失、顶层或嵌套字段、资格过期 |
| 写操作 | 连点、超时、重复请求、服务端拒绝、状态未知、凭据失效、重入与去重 |
| 支付退订 | 支付回跳不作为成功凭据、订单核查、取消和退订可逆性、账务一致性 |
| 数据保护 | 请求与响应日志脱敏、异常信息不泄露令牌、密钥回收、交付文件敏感扫描 |

禁止以真实收费、批量短信或批量订购作为默认验收方式。业务写测试使用明确授权的测试账号、额度与环境；本次工作仅进行本地静态分析、抓包解析及合成密码协议验证。

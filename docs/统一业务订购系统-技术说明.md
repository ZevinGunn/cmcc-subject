# 统一业务订购系统技术说明

版本：V1.0  
日期：2026-07-24  
目标系统：`bj-mobile-business-local`

## 1. 技术结论

本系统在现有 Vue 3 + Vite + Express 应用内增加统一订购域。统一层只管理目录、会话、状态、锁、幂等、脱敏和公共响应；北移、中移商城、网格通继续使用各自独立的认证和传输协议。

现有能力复用如下：

| 现有模块 | 复用方式 |
|---|---|
| `portalClient.js` | 北移继续使用门户 AES/RSA、WAF、重放版本和 CookieJar |
| `sessionStore.js` | 北移订购关联现有登录 session；不把商城/网格通敏感上下文持久化 |
| `customOrderService.js` | 复用已验证的 `compositeCommit`、短信二次确认和结果查询设计 |
| `requestWithJar()` | 三平台统一网络出口，增加 URL 查询脱敏和最终提交不重试能力 |
| `cookie-app` | 移植新零售协议算法和请求字段，不复制账号库与凭据 |
| 已有 HAR/保存源码文档 | 固化端点、字段来源、业务码和未知证据边界 |

## 2. 运行栈与依赖

- 后端：Node.js ESM、Express 4、Axios、Tough Cookie、Node `crypto`、Node `test`。
- 前端：Vue 3、Vite 5、Lucide Vue。
- 数据：既有北京移动登录会话使用 JSON 持久化；统一订购会话只保存在内存。
- 部署：Express 同时提供 `/api` 和构建后的前端静态文件，沿用当前 PM2/Nginx/Cloudflare 配置。

不新增数据库，不引入消息队列，不把一次订购流程拆成多个服务。原因是订购会话短、与上游会话强绑定，并且最终提交不能后台自动重试。

## 4. 统一 API 详细说明

### 4.1 创建会话

`POST /api/quick-orders/sessions`

北移请求：

```json
{
  "platform": "north",
  "businessId": "happy_traffic_double",
  "portalSessionId": "<BJ_SESSION_ID>"
}
```

中移请求：

```json
{
  "platform": "retail",
  "businessId": "happy_traffic_double",
  "cookie": "<WX_10086_COOKIE>"
}
```

网格通请求：

```json
{
  "platform": "grid",
  "businessId": "happy_traffic_double",
  "phone": "<MOBILE>",
  "entryUrl": "https://ysmapp.bj.10086.cn/app/channel-web/busiCore/showCustomIndex.action?..."
}
```

### 4.2 准备产品

`POST /api/quick-orders/sessions/:id/prepare`

- 北移：调用专用初始化接口并根据 `resultCode` 判断资格。
- 中移：完成 `userAuth`，加载页面、规格列表并返回实时可选项。
- 网格通：加载入口页面、校验手机号、查询动态档位。

响应中的 `product.options[].id` 是后续唯一允许提交的选项 ID。

### 4.3 选择档位

`POST /api/quick-orders/sessions/:id/select`

```json
{"optionId":"2285851"}
```

- 北移通常只有初始化返回的单一动态选项，仍要求显式选择。
- 中移读取规格详情、协议并执行 `productPreCheck`。
- 网格通只接受当次档位响应中的 `WARE_PLAN_ID`。

### 4.4 发送短信

`POST /api/quick-orders/sessions/:id/sms/send`

```json
{
  "agreed": true,
  "realOrderConfirmed": true,
  "confirmationId": "a4d97d7a72a84a03b9d2a13d3e990afe"
}
```

`agreed` 和 `realOrderConfirmed` 必须为 true，`confirmationId` 必须是前端在真实订购确认弹窗中生成的 8 至 80 位标识。北移在此动作中先调用首次 `compositeCommit`，因此该端点也使用单会话锁和确认标识幂等；首次提交语义不明时直接进入 `UNKNOWN`。资格未通过时拒绝继续。短信冷却为 60 秒，服务端按最后成功发送时间控制。

### 4.5 最终确认

`POST /api/quick-orders/sessions/:id/confirm`

```json
{
  "smsCode": "<SMS_CODE>",
  "confirmationId": "a4d97d7a72a84a03b9d2a13d3e990afe",
  "agreed": true,
  "realOrderConfirmed": true
}
```

成功结果：

```json
{
  "stage": "FINISHED",
  "lastResult": {
    "accepted": true,
    "uncertain": false,
    "code": "0",
    "message": "订购请求已受理",
    "retryAllowed": false
  }
}
```

未知结果：

```json
{
  "stage": "UNKNOWN",
  "lastResult": {
    "accepted": false,
    "uncertain": true,
    "code": "RESULT_UNKNOWN",
    "message": "结果未确认，请先通过官方渠道查询，不要重复提交",
    "retryAllowed": false
  }
}
```

## 5. 北移适配器

### 5.1 认证和加密

适配器必须取得现有 `sessionStore` 中已完成门户登录的会话。门户请求沿用：

- OAuth Bearer `accessToken`。
- WAF `XEbtxIBt`。
- 每会话随机 16 字符 AES key。
- 服务端公钥封装后的 `X-DATA-TOKEN`。
- 加密递增 `X-REPLAY-VERSION`。
- POST JSON 正文的 AES-ECB/PKCS7 兼容加密。

### 5.2 流程和接口

```text
HCLLFFInitData
  -> compositeCommit
  -> sendDXSMS 或 sendDXSMSV2
  -> checkDxCodeForMT
  -> 原 payload 再次 compositeCommit
  -> 可选 showBLJG
```

初始化：

```text
POST /nwt/portal-bff/api/mPersonBusi/v1.0/HCLLFFInitData
```

固定业务字段：

| 字段 | 值/来源 |
|---|---|
| `packageId` | `55412` |
| `packageCode` | `HCLLFF26` |
| `pitemShowCode` | `KT` |
| `productShowCode` | 初始化响应 `productCode` |
| `mtOtherParams` | `1-<plan_fee>` |

首次和短信后二次提交使用完全相同的逻辑 payload：

```json
{
  "common": {"operType": "commitProductNew"},
  "body": {"content": {
    "packageId": "55412",
    "packageCode": "HCLLFF26",
    "productShowCode": "<DYNAMIC_PRODUCT_CODE>",
    "pitemShowCode": "KT",
    "mtOtherParams": "1-<PLAN_FEE>"
  }}
}
```

`resultCode=00` 表示初始化可继续；`33` 表示已办理；其他值按上游提示返回不可办理。首次 `compositeCommit` 返回 `need_sms_check` 或 `smsVerification` 时保存 `typeKey`、`smsType` 和原 payload。验证码接口仅在 `result=00000` 后允许二次提交。

## 6. 中移商城适配器

### 6.1 认证和业务加密

登录报文：AES-128-CBC、PKCS7、输出大写 Hex。

```text
key = 1234123412ABCDEF
iv  = ABCDEF1234123412
```

业务报文：AES-256-CBC、PKCS7、输出 Base64URL（保留兼容填充解码）。

```text
key = 03054BD8937F62FA8FE72F00012B9658
iv  = 82787D91132E6AE5
```

入口主域为 `https://wx.10086.cn`，网关前缀为 `/website/nrapigate/`。`userAuth` 返回的 Token 写入 `Authorization`，用户省市、`centerFlag`、`secondChannel` 按响应进入后续请求头或业务字段。

### 6.2 欢畅流量样例产品

| 字段 | 样例值 | 来源 |
|---|---|---|
| `personalPageId` | `2026042315380104102006140` | 保存页面/HAR |
| `productId` | `2180820` | 页面响应 |
| `productCode` | `12287504` | 页面响应 |
| `normId` | `2285851` | 页面组件/实时档位 |
| `packageId` | `111602054465` | 规格 `data.productCode` |
| `ptId` | `200100574` | 协议响应 |

这些是样例基线，不允许直接跳过实时页面、规格、协议和预校验查询。

### 6.3 最小流程

```text
userAuth
  -> newProductPersonalPageById
  -> norm
  -> queryProtocol
  -> productPreCheck
  -> sendSms
  -> createOrder
```

准备阶段可调用 `queryPolicy`、`queryRelevancy`、商户、机会和优惠接口完善展示，但不得让辅助接口失败阻断最小订购链。

核心端点：

| 端点 | 作用 | 成功判定 |
|---|---|---|
| `nrauth/auth/encryt/userAuth` | 商城 SSO | `returnCode=0` 且存在 Token/用户信息 |
| `nrmix/product/newProductPersonalPageById` | 页面与产品 | `returnCode=0` 且页面启用 |
| `nrmix/product/norm` | 规格详情 | `returnCode=0` 且规格 ID 匹配 |
| `nrproduct/atom/protocol/queryProtocol` | 实时协议 | `returnCode=0` |
| `nrmix/preCheck/productPreCheck` | 资格预校验 | 外层 `0`，内层 JSON `status=0` |
| `nrmix/sms/sendSms` | 业务验证码 | 外层 `0` 且 `data.status=0` |
| `nrmix/order/createOrder` | 最终订购 | `returnCode=0` 且业务数据为受理成功 |

最终验证码同时写入 `password`、`cmgSmsCode`、`verifyCode`。订单字段 `productId`、`productCode`、`normid`、`packageId` 和协议字段必须保留各自来源语义，禁止按同名字段互换。

## 7. 网格通适配器

### 7.1 入口和传输

唯一允许入口：

```text
https://ysmapp.bj.10086.cn/app/channel-web/busiCore/showCustomIndex.action
```

入口要求 `submitWarePackageId`、`channel`、`code`、`empCode`、`nbc`。系统将其映射为隐藏表单字段：

| 入口参数 | 表单字段 |
|---|---|
| `submitWarePackageId` | `submitWarePackageId` |
| `channel` | `submitChannel` |
| `code` | `submitCode` |
| `empCode` | `submitEmpCode` |
| `nbc` | `nbc` |

所有 XHR 使用 `application/x-www-form-urlencoded; charset=UTF-8`，保留同一 CookieJar 和 Referer。不套用北移或中移加密。

### 7.2 流程

```text
showCustomIndex.action
  -> customerValidateAndIsHaveOrderedForHCLLFFHD.action
  -> queryWarePlansGetPlanFeeFormBIAndTERMBUNDCheck001.action
  -> sendMessageWithDxFromRedisByWareTypeId.action
  -> checkSmsCode.action
  -> commitCYDS.action
```

固定页面编码：

```text
submitWarePackageId=A1000770
submitWareTypeId=B1001605
submitChannel=app_share
```

档位接口 `entity` 是 JSON 字符串，二次解析后读取 `warePlans`。`WARE_PLAN_ID` 为真实选项 ID，`PLAN_FEE` 和 `arpuAvg` 按带单位字符串展示。

短信成功响应的 `errorMsg` 是 `submitCheckCodeId` 挑战号。验证码校验成功响应的 `entity` 是最终一次性 `token`。`commitCYDS.action` 使用普通表单，最终响应可能是 HTML 或跳转；只有明确成功文案或已确认业务码才映射 `FINISHED`，其余映射 `UNKNOWN`。

## 8. 错误映射

| 公共错误码 | 场景 | 是否允许重试 |
|---|---|---|
| `QUICK_ORDER_SESSION_NOT_FOUND` | 会话不存在或过期 | 重新开始 |
| `QUICK_ORDER_INVALID_STAGE` | 操作顺序错误 | 按当前阶段继续 |
| `QUICK_ORDER_OPTION_NOT_FOUND` | 档位不是实时返回值 | 刷新产品 |
| `QUICK_ORDER_SMS_COOLDOWN` | 发送过频 | 倒计时后发送 |
| `QUICK_ORDER_CONFIRMATION_REQUIRED` | 未完成真实订购确认 | 补充确认 |
| `QUICK_ORDER_ALREADY_RUNNING` | 最终提交执行中 | 等待，不重发 |
| `UPSTREAM_AUTH_FAILED` | 登录/Cookie/入口失效 | 更新登录态 |
| `UPSTREAM_REJECTED` | 明确业务拒绝 | 按提示处理 |
| `SMS_CODE_INVALID` | 验证码格式或明确错误 | 当前流程内重输 |
| `RESULT_UNKNOWN` | 最终提交传输或语义不确定 | 禁止重下单，官方查询 |

## 9. 网络和日志实现

`requestWithJar` 增加可配置的 `logUrl` 或统一 URL 清洗：保留协议、主机、路径和非敏感参数，敏感参数替换为 `[REDACTED]`。最终提交显式设置 `maxAttempts=1`。其余读取请求维持最大 2 至 3 次网络重试，但业务拒绝不重试。

外部日志示例：

```json
{
  "type": "quickOrder:step",
  "platform": "grid",
  "stage": "SMS_SENT",
  "step": "send-sms",
  "status": 200,
  "businessCode": "success",
  "durationMs": 328
}
```

## 10. 配置项

| 环境变量 | 默认值 | 说明 |
|---|---|---|
| `QUICK_ORDER_SESSION_TTL_MS` | `900000` | 未完成订购会话有效期 |
| `QUICK_ORDER_RESULT_TTL_MS` | `600000` | 最终结果幂等保留期 |
| `QUICK_ORDER_SMS_COOLDOWN_MS` | `60000` | 短信发送冷却 |
| `RETAIL_ORIGIN` | `https://wx.10086.cn` | 中移商城允许主域 |
| `GRID_ORIGIN` | `https://ysmapp.bj.10086.cn` | 网格通允许主域 |

平台产品编码属于版本化目录常量，不作为任意环境变量开放，防止运维误配触发错误产品。

## 11. 已知证据边界

- 中移 HAR 最终返回验证码错误，未包含成功订单样例。
- 北移 HAR 未捕获最终成功，但页面源码完整定义了短信后二次提交。
- 网格通 HAR 在验证码错误处结束，未捕获 `commitCYDS` 和成功结果页。
- 因此首次真实人工联调前，三个适配器对未确认分支必须保守返回 `UNKNOWN`，不得扩展成功枚举。

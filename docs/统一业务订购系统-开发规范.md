# 统一业务订购系统开发规范

版本：V1.0  
日期：2026-07-24  
适用项目：`bj-mobile-business-local`（线上域名 `bmcc.1008086.xyz`）  
适用范围：北移业务订购、中移商城业务订购、网格通业务订购

## 1. 目的和强制原则

本文规定统一业务订购系统的工程、安全、接口、状态、测试和上线要求。所有真实订购能力必须同时满足以下原则：

1. 三个平台协议独立实现，不混用域名、认证、加密、字段和成功判定。
2. 产品、档位、协议和挑战参数以当次上游响应为准，客户端不得注入未返回的 ID。
3. 真实提交必须经过“页面确认 + 服务端确认标识”双重确认。
4. 最终提交使用单次锁和幂等键；超时或连接中断进入 `UNKNOWN`，不得自动重下单。
5. 自动化测试只允许 mock 上游，不发送真实短信，不执行真实订购。
6. Cookie、Token、验证码、手机号、姓名、入口 `nbc`、推荐码、员工码和加密材料不得写入日志。
7. HTTP 200 只代表传输完成，业务成功必须按平台响应契约判断。

## 2. 系统边界

### 2.1 系统负责

- 复用北京移动登录会话，建立北移门户订购上下文。
- 接受中移商城的有效 Cookie，完成商城 SSO、产品准备、预校验、协议、短信和提交。
- 接受可信网格通入口 URL，维持表单会话，完成资格、档位、短信、校验和提交。
- 对外提供统一目录、会话、准备、选档、短信、确认和会话销毁 API。
- 对最终结果返回 `FINISHED`、`FAILED` 或 `UNKNOWN`，并给出禁止重复提交提示。

### 2.2 系统不负责

- 生成或猜测网格通 `nbc`、推荐码、员工码。
- 绕过上游登录、验证码、协议确认、资格校验或风控。
- 把 HAR 中的 Cookie、Token、验证码、挑战号或一次性 token 用于生产。
- 在结果未知时自动补单；补查能力未被上游正式证明前，只提示通过官方渠道核验。
- 将 `cookie-app` 的账号数据库、密钥库或历史凭据复制到本项目。

## 3. 代码组织规范

后端统一功能放在 `backend/src/services/quickOrders/`：

```text
quickOrders/
  catalog.js              业务目录与平台常量
  errors.js               稳定错误类型
  sessionStore.js         短生命周期订购会话
  service.js              公共状态机、锁、幂等和适配器调度
  adapters/
    north.js               北京移动 portal-bff
    retail.js              中移新零售商城
    grid.js                网格通表单链路
```

统一路由放在 `backend/src/routes/quickOrders.js`。前端使用独立页面 `frontend/src/pages/QuickOrderPage.vue`，平台和步骤组件仅在存在实际复用时拆分。

每个适配器必须实现统一能力：

```text
createContext(input, dependencies) -> privateContext
prepare(session)                  -> product view
select(session, selection)        -> selection view
sendSms(session)                  -> cooldown view
confirm(session, smsCode)         -> final result
dispose(session)                  -> void
```

适配器只返回规范化领域对象，不把未脱敏的上游响应直接返回浏览器。

## 4. 编码规范

### 4.1 JavaScript

- 使用项目现有 ESM、Node.js 内置 `node:test` 和 Vue 3 Composition API。
- 输入边界必须显式校验类型、长度、枚举和格式；禁止仅依赖前端校验。
- URL 使用 `URL`、`URLSearchParams` 解析和编码，不手工拼接敏感查询串。
- 表单使用 `URLSearchParams` 编码；JSON 使用 `JSON.stringify`；禁止正则替换模拟协议解析。
- 时间统一保存为毫秒时间戳，对外使用 ISO 8601；北京业务显示时间明确使用 `Asia/Shanghai`。
- 平台协议解析采用小型纯函数，并为嵌套 JSON、空字段和异常响应提供测试。
- 只有跨函数仍不直观的协议约束才写注释，注释说明“为什么”，不复述代码。

### 4.2 命名

- 公共平台标识固定为 `north`、`retail`、`grid`。
- 公共阶段固定为 `INITIALIZED`、`AUTHENTICATED`、`PRODUCT_READY`、`SELECTION_READY`、`SMS_SENT`、`SUBMITTING`、`FINISHED`、`FAILED`、`UNKNOWN`。
- 平台原始字段保留上游大小写；领域字段使用 `camelCase`。
- 错误码使用大写下划线并以领域前缀区分，例如 `QUICK_ORDER_INVALID_STAGE`、`RETAIL_AUTH_FAILED`。

## 5. API 规范

### 5.1 响应包装

成功响应：

```json
{
  "ok": true,
  "data": {}
}
```

失败响应：

```json
{
  "ok": false,
  "message": "可直接展示给操作员的中文信息",
  "errorCode": "STABLE_MACHINE_CODE"
}
```

业务校验失败可保持项目现有 HTTP 200 兼容形式；新增 API 对明显请求错误使用 400、会话不存在使用 404、状态冲突使用 409、频率限制使用 429。调用方始终以 `ok` 为首要判断。

### 5.2 会话 API

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/api/quick-orders/catalog` | 返回平台、产品、字段能力和风险提示 |
| POST | `/api/quick-orders/sessions` | 建立平台订购会话 |
| GET | `/api/quick-orders/sessions/:id` | 读取脱敏会话状态 |
| POST | `/api/quick-orders/sessions/:id/prepare` | 认证并加载实时产品/档位 |
| POST | `/api/quick-orders/sessions/:id/select` | 选择后端返回的档位并完成预校验/协议查询 |
| POST | `/api/quick-orders/sessions/:id/sms/send` | 发送当次订购验证码 |
| POST | `/api/quick-orders/sessions/:id/confirm` | 校验验证码并执行唯一一次最终提交 |
| DELETE | `/api/quick-orders/sessions/:id` | 销毁订购会话和敏感上下文 |

### 5.3 版本和兼容

- V1 API 字段只追加，不重命名、不改变类型。
- 新的平台原始字段不得直接提升为公共必填字段；优先封装为平台输入对象。
- 平台返回未知枚举时保留原值并返回安全错误，不按相近含义猜测。

## 6. 状态机规范

允许的主路径：

```text
INITIALIZED -> AUTHENTICATED -> PRODUCT_READY -> SELECTION_READY
            -> SMS_SENT -> SUBMITTING -> FINISHED
                                     -> FAILED
                                     -> UNKNOWN
```

平台可在一次 `prepare` 内跨越认证阶段，但对外状态必须单调前进。以下行为必须拒绝：

- 未准备产品直接选档。
- 选择浏览器自行构造的档位 ID。
- 未选档或未接受必需协议时发送短信。
- 未发送短信直接确认。
- 在 `SUBMITTING`、`FINISHED` 或 `UNKNOWN` 再次确认。
- 使用另一个会话的挑战号、产品或验证码上下文。

## 7. 安全规范

### 7.1 输入和 SSRF

- 北移不接受自定义域名或接口路径。
- 中移 Cookie 最大 32 KiB，拒绝 CR/LF；产品仅允许目录中的固定业务。
- 网格通入口 URL 仅允许 `https://ysmapp.bj.10086.cn/app/channel-web/busiCore/showCustomIndex.action`。
- 网格通业务端点使用代码内允许列表，不采信页面返回的任意提交地址。
- 所有 ID 使用白名单字符和长度限制；短信验证码只接受 6 位数字。

### 7.2 敏感信息

| 数据 | 内存 | 持久化 | 日志 | 浏览器返回 |
|---|---|---|---|---|
| 北京移动访问令牌 | 允许 | 沿用现有会话策略 | 禁止 | 仅布尔状态 |
| 中移 Cookie/Authorization | 允许 | 禁止 | 禁止 | 禁止 |
| 网格通 `nbc`/推荐码/员工码 | 允许 | 禁止 | 禁止 | 仅 `hasEntryContext` |
| 手机号 | 允许 | 仅既有登录会话 | 掩码 | 掩码 |
| 短信验证码/挑战号/token | 允许至流程结束 | 禁止 | 禁止 | 仅存在性布尔值 |
| 上游完整响应 | 必要时短暂存在 | 禁止 | 结构化脱敏摘要 | 仅规范化字段 |

订购会话默认 15 分钟过期，最终状态保留不超过 10 分钟用于幂等响应。进程退出后不恢复未完成的外部订购上下文。

### 7.3 日志脱敏

- 记录 URL 时移除 `nbc`、`code`、`empCode`、Token、验证码和所有疑似认证查询参数。
- 请求体只记录平台、阶段、是否含凭据、产品/档位的非敏感业务 ID。
- 外部响应记录 HTTP 状态、平台业务码、耗时和结构摘要，不记录密文正文。
- 中移加密报文也按敏感正文处理；“已经加密”不等于可以记录。

## 8. 幂等、并发和结果未知

- 每个订购会话的短信/北移首次提交和 `confirm` 分别只有一个执行锁。
- `sms/send` 与 `confirm` 都必须携带同一个 8 至 80 位 `confirmationId`；相同会话和标识返回首次最终结果。
- `confirmationId` 与平台会话绑定，不能跨会话使用。
- 最终提交前写入 `SUBMITTING`，完成后才写 `FINISHED` 或 `FAILED`。
- 最终提交超时、连接重置、响应无法解析或网格通结果页语义不明确时写 `UNKNOWN`。
- `UNKNOWN` 响应必须包含 `retryAllowed=false` 和官方渠道核验提示。
- 网络层对最终提交设置 `maxAttempts=1`；准备、查询类请求最多可按既有策略重试。

## 9. 前端交互规范

- 第一屏直接展示三平台工作台，不创建营销落地页。
- 平台使用分段控件；步骤使用固定高度进度条，动态文本不得引起布局跳动。
- Cookie 和入口 URL 使用密码型或可隐藏输入，提供明确的“已载入”状态，不回显原值。
- 产品档位只能从后端列表选择；价格、低消、规则和协议按原始字符串展示。
- 发送短信后显示倒计时；重发成功后清除旧验证码并替换挑战上下文。
- 最终确认弹窗必须列出平台、产品、档位、费用/低消、生效方式和关键风险。
- 确认按钮使用危险操作视觉；提交中不可关闭或重复点击。
- `UNKNOWN` 使用中性警告，不显示“失败后重试”按钮。

## 10. 测试规范

### 10.1 必测层级

1. 纯函数单元测试：加解密、嵌套 JSON、入口 URL、档位归一化、结果判断。
2. 适配器契约测试：每个平台完整成功链、上游业务失败、短信失败、验证码错误、最终超时。
3. 服务状态机测试：非法顺序、跨会话访问、锁、幂等、TTL、`UNKNOWN` 禁止重试。
4. 路由集成测试：输入校验、响应包装、敏感字段不回传。
5. 前端构建和浏览器测试：桌面与移动端、错误态、长文本、弹窗和按钮锁。

### 10.2 禁止事项

- CI 或本地自动化不得访问三个平台真实订购端点。
- 不使用历史验证码、Cookie、token 或 HAR 进行重放测试。
- 不以“接口返回 HTTP 200”作为成功断言。
- 不通过降低超时或跳过协议来缩短测试。

## 11. 上线门禁

上线前必须全部通过：

- 后端 `npm test`、前端 `npm run build`。
- 三个平台 mock 成功链和所有高风险异常链。
- 日志样本确认无 Cookie、Token、验证码、手机号全量和网格通入口密钥。
- 浏览器桌面和移动端无重叠、溢出、不可点击或状态跳变。
- 使用测试号码的人工联调分平台进行，最终提交由操作员明确确认。
- 首次真实联调后补录中移成功响应、北移成功结果、网格通成功结果页与可查询流水。

## 12. 变更管理

平台页面、接口、加密或业务码发生变化时：

1. 保存新的 HAR 与源码并脱敏归档。
2. 更新证据文档和适配器契约测试夹具。
3. 先在 mock 中复现，再修改实现。
4. 重新完成安全、构建、浏览器和人工联调门禁。
5. 未确认的响应分支一律映射为 `UNKNOWN`，不得临时放宽成功判定。

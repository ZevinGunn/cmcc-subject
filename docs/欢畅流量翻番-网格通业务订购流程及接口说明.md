# 欢畅流量翻番：网格通业务订购流程及接口说明

## 1. 文档目的与结论

本文基于“欢畅网格通.zip”保存的网格通页面源码与“欢畅网格通.har”实际调用记录，完整还原欢畅流量翻番活动在网格通页面中的订购链路、接口顺序、表单字段、响应状态、短信确认机制、最终提交条件与联调边界。

网格通页面位于 `ysmapp.bj.10086.cn/app/channel-web`，与中移新零售商城、北移 portal-bff 都不是同一套接口。该页面由推荐/渠道链接进入，用户手工输入北京移动手机号，服务端完成客户资格及已订购判断，再返回可办档位。确认档位后，页面发送短信、校验验证码；只有验证码校验成功并取得一次性 `token`，才以普通 HTML 表单提交 `commitCYDS.action`。

> 核心结论：网格通业务请求没有观察到 AES/RSA 业务报文加密，也没有 `Authorization` 请求头。四个已捕获业务 XHR 均为 `application/x-www-form-urlencoded`。安全与会话约束主要依赖入口参数 `nbc`、短信挑战号 `submitCheckCodeId`、验证码和校验成功后返回的提交 `token`。这些值必须按当前页面会话实时取得，不能复制历史 HAR。

本次 HAR 在验证码错误处结束，没有捕获验证码校验成功响应，也没有出现最终 `commitCYDS.action` 请求和订购成功页。因此，本文对最终提交的端点、入参和前置条件可依据源码完整说明，但不能给出真实成功响应结构或订单号字段。

## 5. 完整订购流程

### 5.1 页面进入与初始化

1. 使用平台生成的推荐/渠道链接打开 `showCustomIndex.action`，入口至少携带页面套餐包、渠道、推荐代码、员工代码和 `nbc`。
2. 页面载入活动标题、业务规则、业务类型 `B1001605`、短信接口、档位接口和最终提交动作。
3. 页面初始隐藏档位与提交区域，等待用户输入手机号并完成服务端校验。
4. 入口参数写入隐藏表单，后续所有业务接口都序列化同一个 `submitForm`。

入口示例已脱敏：

```text
GET /app/channel-web/busiCore/showCustomIndex.action
  ?submitWarePackageId=A1000770
  &channel=app_share
  &code=<REFERRAL_CODE>
  &empCode=<EMP_CODE>
  &nbc=<NBC>
```

### 5.2 手机号与资格校验

1. 前端移除手机号空格并要求长度为 11 位。
2. 页面将逻辑手机号写入 `submitPhoneNO`，清空上一次业务类型、档位、已选说明和验证码。
3. 调用客户校验接口。
4. 仅当 `errorCode=success` 时将 `iscustomerValidate=true`，锁定手机号输入框并继续选择业务。
5. 校验成功后页面不允许直接修改手机号；需要退出并重新进入受理页，避免旧资格状态与新号码混用。

### 5.3 查询并选择档位

1. 页面选中业务类型 `B1001605` 并写入 `submitWareTypeId`。
2. 调用档位查询接口，响应外层 `entity` 是 JSON 字符串，需要再次解析。
3. 展示 `arpuAvg`，按 `warePlans` 渲染当前用户可办档位。
4. 用户选择档位后写入 `submitWarePlanId`。
5. 页面将“活动名称+档位名称”写入 `submitSelectedInfo`，同时生成短信确认框说明。

### 5.4 发送短信验证码

1. 页面确认客户校验已通过，且 `submitWareTypeId`、`submitWarePlanId` 均非空。
2. 清空验证码输入框，锁定发送按钮并启动 60 秒倒计时。
3. 调用短信发送接口。
4. 当 `errorCode=success` 时，把响应 `errorMsg` 写入 `submitCheckCodeId`。
5. `submitCheckCodeId` 是本次短信挑战号，不是用户短信验证码。重发后应使用最新挑战号。

### 5.5 校验验证码与最终提交

1. 用户输入验证码，页面写入 `submitCheckCode`。
2. 页面同步调用 `checkSmsCode.action`，同时提交挑战号和验证码。
3. 当校验接口返回 `errorCode=error` 时，只展示错误并恢复确认按钮，不提交业务。
4. 当校验接口返回非 `error` 时，源码把 `entity` 写入隐藏字段 `token`。
5. 页面读取业务项配置的 `commit_action`，本活动为 `busiCore/commitCYDS.action`。
6. 页面以普通 HTML 表单提交完整 `submitForm`，浏览器进入服务端返回的结果页。

> 最终业务提交必须发生在验证码校验成功并取得 `<COMMIT_TOKEN>` 之后。本次 HAR 的验证码错误，因此没有最终提交。任何绕过校验、复用旧挑战号或提交空 `token` 的实现都不符合页面状态机。

## 6. 公共传输与表单契约

### 6.1 HTTP 特征

| 项目 | 已捕获行为 | 实现要求 |
|---|---|---|
| 协议 | HAR 使用 HTTPS | 生产只使用 HTTPS；保存源码中的旧 `http:80` base 不应作为新实现依据 |
| XHR 方法 | 4 个业务接口均为 POST | 不改写为 GET，不把手机号放入 URL |
| Content-Type | `application/x-www-form-urlencoded; charset=UTF-8` | 使用标准表单编码器 |
| X-Requested-With | `XMLHttpRequest` | XHR 接口按页面行为携带；最终表单跳转不强依赖 |
| Referer | 当前 `showCustomIndex.action` 完整入口地址 | 浏览器自然产生；服务端代理需确认平台正式要求 |
| Authorization | 未捕获 | 不虚构 Bearer Token |
| Cookie | 四个业务 XHR 未捕获 Cookie 请求头 | 不能据此断言接口为公开 API；仍应保留浏览器页面会话与入口参数 |
| 业务报文加密 | 未观察到 | 不套用中移 AES 或北移 AES/RSA 协议 |

### 6.2 公共响应外层

| 字段 | 类型 | 常见值 | 说明 |
|---|---|---|---|
| `errorCode` | String | `success` / `error` | 页面首要成功判定字段 |
| `errorMsg` | String/null | 提示文本或挑战号 | 含义随接口变化，短信发送成功时承载 `submitCheckCodeId` |
| `entity` | String/Object/null | JSON 字符串、提交令牌或空 | 档位接口需要二次 JSON 解析；验证码成功时作为 `token` |
| `errorTitle` | String/null | 错误标题 | 档位查询失败时用于弹窗标题 |

`errorMsg` 和 `entity` 都是被复用的通用槽位，客户端必须按“接口 + 状态”解释，不能建立全局固定字段语义。

### 6.3 公共表单字段字典

| 字段 | 类型 | 必填级别 | 来源 | 说明 |
|---|---|---|---|---|
| `submitPhoneNO` | String | 资格校验起必填 | 用户输入 | 11 位北京移动手机号；日志脱敏 |
| `submitWareTypeId` | String | 档位查询起必填 | 页面业务项 | 本活动为 `B1001605` |
| `submitWarePlanId` | String | 短信发送起必填 | 档位查询响应 | 本次为 `C1004150`；不能预先硬编码为所有用户通用 |
| `submitWarePackageId` | String | 全流程必填 | 入口链接/页面 | 本页面为 `A1000770` |
| `nbc` | String | 全流程建议必填 | 入口链接/页面 | 会话或链接校验值，按当前页面传递，不解析、不落日志 |
| `submitCheckCode` | String | 验证码校验及最终提交必填 | 用户输入 | 当前短信验证码 |

## 8. 状态机与页面控制

### 8.1 业务状态

| 状态 | 进入条件 | 允许动作 | 禁止动作 |
|---|---|---|---|
| `INIT` | 页面加载完成 | 输入手机号 | 查询档位、发送短信、提交 |
| `CUSTOMER_VALIDATED` | 客户接口 `errorCode=success` | 查询/选择可办档位 | 修改手机号后沿用旧状态 |
| `PLAN_SELECTED` | 选择服务端返回档位 | 发送短信 | 使用未返回或篡改档位 |
| `SMS_SENT` | 短信发送成功并保存挑战号 | 输入并校验验证码、按倒计时重发 | 用旧挑战号配新验证码 |
| `SMS_VERIFIED` | 校验成功并保存 token | 单次最终提交 | 空 token 提交、重复校验绕过 |
| `SUBMITTING` | 已发起 `commitCYDS` | 等待结果页 | 自动重试、重复点击 |
| `SUCCESS/FAILED` | 结果页明确判定 | 保存结果或展示错误 | 仅凭 HTTP 200 判成功 |
| `UNKNOWN` | 网络中断或超时，结果不可知 | 查询订单/人工核验 | 自动再次下单 |

### 8.2 前端控制建议

- 手机号校验成功后锁定输入；若需更换号码，重新初始化整个页面状态。
- 档位列表只接受当前资格查询响应中的 ID，不接受 URL 或客户端任意注入。
- 短信发送、验证码校验和最终提交分别使用独立的加载态与点击锁。
- 重发短信后覆盖 `submitCheckCodeId`，清空旧验证码和旧提交 token。
- 验证码校验失败后恢复确认按钮，但不清除当前档位。
- 最终提交前再次核对手机号、档位、挑战号、验证码和 token 均属于同一会话。
- 最终提交超时进入“结果未知”，禁止自动重发；需要订单状态查询或人工核验。

## 10. 响应判定、异常与幂等

### 10.1 统一判定原则

| 场景 | 正确判定 | 错误做法 |
|---|---|---|
| 客户校验 | `errorCode=success` | HTTP 200 即通过 |
| 档位查询 | 外层成功且二次解析后 `warePlans` 非空 | 忽略字符串化 `entity` |
| 短信发送 | `errorCode=success` 且保存 `errorMsg` 挑战号 | 把 `errorMsg` 当普通成功文案丢弃 |
| 验证码校验 | 非错误分支且 `entity` 可作为 token | 验证码有 6 位就直接提交 |
| 最终订购 | 结果页明确业务成功并保存订单/流水 | 仅凭 HTTP 200 或页面跳转成功 |

### 10.2 常见异常处理

| 异常 | 页面/接口表现 | 建议处理 |
|---|---|---|
| 手机号格式错误 | 本地长度校验失败 | 不发请求，提示重新输入 |
| 非目标用户或已订购 | 客户校验 `errorCode=error` | 展示服务端 `errorMsg`，停止流程 |
| 无可办档位 | `warePlans` 空 | 提示不可办理，不展示提交区 |
| 档位接口返回非 JSON entity | 二次解析失败 | 记录脱敏错误，停止办理 |
| 短信发送失败 | `errorCode=error` 或网络失败 | 恢复发送按钮，不生成挑战状态 |
| 验证码错误 | 本次为“您输入的短信验证码不正确！” | 保持档位，允许重新输入或按规则重发 |
| 挑战号过期/不匹配 | 预计校验失败 | 使用最新短信发送响应，禁止复用历史值 |
| 最终提交超时 | 浏览器未得到明确结果页 | 进入 `UNKNOWN`，查询状态或人工核验 |
| 重复点击 | 多次触发表单提交 | 前端立即锁定，后端按用户+业务+挑战窗口幂等 |

### 10.3 幂等与防重建议

- 前端在点击确认时立即禁用按钮，直到验证码校验失败或最终结果明确。
- 后端幂等键建议覆盖脱敏用户标识、活动业务类型、档位、短信挑战号和短时间窗。
- 不对 `commitCYDS.action` 自动重试；网络失败不等于业务失败。
- 已订购用户优先由客户校验接口阻断，最终提交仍需服务端二次防重。
- 每次短信重发视为新的挑战上下文，旧 token 和旧验证码全部失效处理。

## 12. 上线验收清单

- 已把网格通作为独立平台适配器，不复用中移或北移加密协议。
- 入口参数由可信渠道生成，`nbc`、推荐代码和员工代码不硬编码。
- 客户校验成功后才允许查询档位，手机号变更会重置完整状态。
- 档位只采用服务端 `warePlans` 返回值，三个商品层级编码严格区分。
- 正确处理 `entity` 的 JSON 字符串二次解析。
- `PLAN_FEE`、`arpuAvg` 按带单位字符串展示，不参与不安全的浮点金额运算。
- 短信发送成功后保存 `errorMsg` 为挑战号，重发时覆盖旧挑战。
- 验证码错误不会调用 `commitCYDS.action`。
- 验证码成功响应的 `entity` 作为一次性提交 token，空 token 禁止提交。
- 最终提交单击锁定、后端幂等，超时进入结果未知状态。
- HTTP 200 不作为最终订购成功条件。
- 已补录正式环境的成功结果页、订单号/流水号和结果查询方式。
- 日志、监控和客服导出均已完成敏感字段脱敏。

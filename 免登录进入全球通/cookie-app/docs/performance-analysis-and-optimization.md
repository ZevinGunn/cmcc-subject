# 首屏与接口性能诊断及优化方案

## 1. 结论

当前“整体请求略慢、首屏加载久”的主因不是本机网络连接，而是首屏数据链路重复、数据库读取存在 N+1 查询与重复解密、V2 对所有子路由无差别请求数据，以及前端所有页面打入一个主包。

2026-07-20 在本机 PM2 服务 `127.0.0.1:3101` 的未鉴权基线：

| 请求 | 状态 | TTFB | 总时间 |
| --- | ---: | ---: | ---: |
| `/v2` | 200 | 35.5ms | 35.5ms |
| `/api/accounts?includeDisabled=1` | 403 | 3.8ms | 3.8ms |
| `/api/tasks/list?limit=50` | 403 | 2.1ms | 2.1ms |
| `/api/tasks/schedules/list` | 403 | 1.4ms | 1.5ms |
| `/api/auth/me` | 401 | 1.4ms | 1.4ms |
| `/api/auth/accounts` | 401 | 1.2ms | 1.3ms |
| `/api/auth/daily-tasks` | 401 | 2.1ms | 2.2ms |

这些数据只证明 TCP、Express 和无数据库业务的鉴权失败路径很快，不能替代登录态性能数据。优化验收必须追加登录用户和管理员会话下的 P50/P95 测量。

## 2. 根因证据

### 2.1 public 串行且重复请求

`PublicLogin.tsx` 首次加载先请求 `/api/auth/me`；成功后等待 `/api/auth/accounts`；账号返回后再发起 `/api/auth/daily-tasks`。这形成至少三段关键链路。

`/api/auth/accounts` 和 `/api/auth/daily-tasks` 都调用 `listUserAccountSummaries(user.id)`。后者每次都会：

1. 查询邀请码绑定账号并执行账号绑定更新。
2. 清理禁用账号绑定更新。
3. 查询用户账号行。
4. 对每个账号串行调用 `getAccountById()`。
5. 对每个账号解密完整记录，再转换摘要。

因此账号数量为 N 时形成 N+1 读取和 N 次大字段解密，紧接着 daily-tasks 又完整重复一次。账号越多，延迟近似线性增长。

### 2.2 会话读取包含写操作

`findCurrentUser()` 每次鉴权都会异步刷新 session `lastSeenAt`。高频轮询接口会持续产生数据库写入、WAL 和锁竞争。会话活跃时间无需每个请求都精确更新。

### 2.3 V2 全路由固定拉取三组数据

`V2App.tsx` 挂载时固定并发请求账号、最近任务、自动化计划。打开系统设置、用户权限、专属链接或未来公告管理页时，也会支付不相关数据成本。

### 2.4 单体前端包

当前构建产物约为：JavaScript 640KB、CSS 56KB（未压缩文件尺寸）。`V2App.tsx` 静态导入全部 V2 页面，同时主应用也静态包含经典管理与 public 页面；浏览器必须下载、解析和执行当前路由不需要的大量代码。

### 2.5 感知性能不足

V2 工作台首次加载只显示居中的 spinner 和文字，真实内容出现后整体布局跳变。即使接口时间不变，用户也会感受到长时间空白和不确定性。

## 3. 第一阶段实施方案

### 3.1 public bootstrap

增加 `GET /api/auth/bootstrap`，一次返回：

- 当前 user payload。
- 用户账号摘要。
- 当日任务 states。
- 公告中心摘要和 popup 候选（如果公告模块已启用）。

服务端只读取一次账号摘要，daily state 直接使用已得到的 account IDs。前端首次访问只等待 bootstrap；原 `/me`、`/accounts`、`/daily-tasks` 保持兼容，用于局部刷新。

### 3.2 消除账号摘要 N+1

实现批量摘要读取：

- 一条 SQL 按 `userId` 读取需要生成 `AccountSummary` 的字段。
- 如现有 `toAccountSummary` 必须依赖加密字段，则先批量读取记录并在内存中映射，禁止循环发 SQL。
- 仅解密摘要真正需要的字段；大 JSON/会话字段保持密文或不读取。
- 邀请码绑定移到 `consumeInviteLink()`、显式绑定操作和一次性数据修复，不在每次列表读取时执行。
- 禁用账号解除绑定移到禁用账号的写路径，不在读路径执行。

### 3.3 会话写节流

仅当 `lastSeenAt` 距当前超过 5 分钟时更新，SQL 带条件：`lastSeenAt is null or lastSeenAt < now() - interval '5 minutes'`。请求仍可异步触发，不阻塞响应。

### 3.4 V2 按路由加载数据

根据 `location.pathname` 决定数据依赖：

| 路由 | 账号 | 任务 | 计划 |
| --- | --- | --- | --- |
| 工作台 | 是 | 是 | 否 |
| 账号/权益/业务 | 是 | 视功能 | 否 |
| 任务/审计 | 视详情 | 是 | 否 |
| 自动化 | 可延后 | 否 | 是 |
| 链接/用户/设置/公告 | 否 | 否 | 否 |

使用“首次进入时加载 + 已有数据复用”策略；刷新按钮只刷新当前页依赖。任务轮询仅在需要任务数据且存在运行中任务时启动。

### 3.5 路由拆包和骨架

用 `React.lazy` + `Suspense` 拆分 public、经典管理和 V2 子页面。优先拆出体积大的业务查询、商城查询、业务订购、用户管理和公告编辑器。V2 工作台使用结构化骨架，固定网格和内容块高度，降低 CLS。

## 4. 第二阶段建议

- 为管理工作台增加轻量 summary endpoint，直接在 SQL 聚合健康数量，不拉取所有完整账号。
- 对只读账号摘要使用 10–30 秒进程内缓存，账号写操作后按用户/管理员维度失效。
- 记录 API server-timing：鉴权、数据库、解密、上游 CMCC 和序列化分别计时。
- 开启反向代理 Brotli/Gzip 和长期缓存：hash 静态资产 `Cache-Control: public,max-age=31536000,immutable`，HTML `no-cache`。
- 对大列表分页或虚拟化，避免接口变快后 DOM 渲染成为新瓶颈。
- 将上游 CMCC 刷新严格置于用户主动操作或后台任务，不进入首屏 bootstrap。

## 5. 指标与验收

在相同数据量、相同进程冷/热状态下记录优化前后数据：

- `/api/auth/bootstrap` 登录态 P50 < 150ms，P95 < 400ms（不含外部 CMCC 请求）。
- public 首屏由 3 段串行请求降为 1 个关键请求。
- 账号摘要 SQL 查询数由 `O(N)` 降为 `O(1)`。
- V2 非数据页首次进入不请求 accounts/tasks/schedules。
- 首屏主路由初始 JS gzip 目标 < 220KB；拆分 chunk 按需加载。
- LCP 目标桌面 < 1.5s、移动模拟 < 2.5s；CLS < 0.1。
- V2 工作台从导航开始 100ms 内出现骨架，数据到达时布局不整体跳动。

每个接口记录至少 20 次热请求的 P50/P95；另记录首次冷请求，避免平均值掩盖长尾。

## 6. 风险与回滚

- 批量摘要必须用现有 summary fixture 做字段逐项对比，防止漏解密或状态判断变化。
- bootstrap 是新增接口，原三个接口保留，因此可通过前端回滚快速恢复。
- 路由按需加载需确认抽屉和跨页操作所需数据，页面发现缺失时可自行加载。
- 短缓存必须在账号更新、删除、登录和绑定后失效；第一阶段可先不缓存，优先消除重复请求和 N+1。
- 性能优化不得改变 CMCC 真实请求次数或订购语义；浏览器验收不触发短信、登录和订购。

## 7. 第一阶段实施结果（2026-07-20）

本次已完成：public bootstrap、用户账号批量摘要、读取路径移除绑定写操作、session 写入 5 分钟节流、V2 路由数据按需加载、任务详情按需加载、应用和 V2 子路由拆包、响应 gzip、hash 静态资源长期缓存，以及工作台结构化骨架。

相同本机服务和数据库下，每个接口连续请求 10 次：

| 指标 | 优化后 P50 | 优化后 P95（含首个冷请求） | 原始响应 | gzip |
| --- | ---: | ---: | ---: | ---: |
| `/api/auth/bootstrap` | 10.8ms | 90.7ms | 82.8KB | 12.5KB |
| `/api/accounts?includeDisabled=1&view=v2` | 29.7ms | 45.5ms | 155.8KB | 23.3KB |
| `/api/tasks/list?limit=50` | 4.9ms | 59.0ms | 25.4KB | 3.7KB |
| `/api/announcements/admin`（空列表） | 0.7ms | 1.7ms | 90B | 未压缩（低于阈值） |

V2 账号响应由约 588KB 降到 156KB；任务列表由约 1.49MB 降到 25KB。任务列表不再返回逐账号日志，用户打开详情时调用现有任务详情接口获取完整数据。

前端构建由单一约 689KB JavaScript 主包改为按路由拆分：入口包 189.7KB（gzip 62.8KB），public chunk 67.2KB（gzip 19.0KB），V2 chunk 61.6KB（gzip 14.8KB），公告管理 chunk 22.3KB（gzip 7.3KB）。入口 gzip 已优于本方案 220KB 目标。

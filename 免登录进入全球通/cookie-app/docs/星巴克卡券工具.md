# 星巴克卡券工具

## 入口与使用

独立页面：`/starbucks`。public 页已关联账号区和用户管理页均有“星巴克卡券”入口。页面与移动手机号业务分开管理，复用当前站点身份；未登录站点时先前往 `/public` 登录，再进入工具。管理员入口使用 `/starbucks?from=users`，返回用户管理。

1. 添加星巴克账号，输入手机号，发送并填写 4 位短信验证码。发送成功后倒计时 60 秒；服务端也限制重复发送和登录尝试。
2. 登录成功后自动查询卡券，也可手动刷新、切换账号或移除本地保存的账号。
3. 默认汇总所有号码的可用卡券，可选择单个号码，组合券名分类、状态、关键词和有效期条件筛选。有效期支持 7/30/90 天内到期、已到期、未知及自定义到期日期区间，日期边界按北京时间计算并包含结束当天。每张主券和子券独立展示，按“账号＋券编号”区分，避免跨账号相同编号混淆。
4. 点击“查看券码”查看单张券；支持单选、分组选择、当前筛选全选及“复制当前筛选”。每个券名分组的“复制本类”支持直接跨号码复制该类卡券。默认复制可用券，切到“全部”等状态可复制对应已使用或过期券码；失效账号需重新登录后操作。
5. 批量读取各账号券码按顺序进行，复用服务端所有权和缓存刷新校验；单次请求不超过 1000 张。某账号读取失败会提示该账号，并允许确认复制其他成功结果。批量复制先打开明细，默认按券名跨号码分类、每条包含账号掩码与有效期；也可选择仅复制券码（每行一条）。

刷新失败保留此前卡券，不表示旧卡券仍可用；确认 HTTP 401 后提示重新登录。HTTP 403 或暂时的网络故障不会直接清除登录。券码读取在查询缓存超过 5 分钟时先刷新，默认可用范围的批量导出再次检查可用状态；明确选择其他状态后允许导出相应券码。本工具不核销卡券。

## 登录和查询协议

参考用户提供的脚本，服务端按下列顺序请求官方域名 `https://bff.starbucks.com.cn`：

| 步骤 | POST 路径 | 主要明文入参 | 结果用途 |
| --- | --- | --- | --- |
| 发短信 | `/app-bff-api/sms/send` | `device`、`phoneNumber`、`template=create-cn`、`token` 为空 | 业务码确认发送成功 |
| 验证码登录 | `/app-bff-api/login` | `cellPhone`、`device`、`loginType=PIN_CODE`、`pin` | 取得临时登录 token |
| 兑换凭证 | `/app-bff-lgc/default/login/access_token` | `grant_type=authorization_code`、`code` 为临时 token | 获取 `access_token`；支持 HTTP 201 |
| 会员信息 | `/app-bff-api/auth/v2/user/detail` | 空对象，携带 Bearer token | 提取 `MEM_` 会员标识；普通失败保留已兑换会话，确认过期时中止 |
| 卡券查询 | `/bff2/user/coupon/list` | `base`、`params.channel=ALL`、`pageNum`、`scene=ME` | 解析 `data.couponList`；带 `appid`、`timestamp` 查询参数 |

请求体使用 AES-256-CBC 加密，发送 `{encrypted: ...}`。密钥按脚本字符串的 UTF-8 字节使用，不能按十六进制解码。签名为 RSA-SHA256，原文为 `2#channel#毫秒时间戳#path#明文query#明文body`。`/bff2/` 使用裸签名，其余相关路径使用带版本、渠道及 nonce 的签名头。兑换凭证额外使用 `X-API-Version: 2.0`、`x-msr-version: 2`。

支持明文 JSON 或加密响应。分页遇到空页、重复页或明确终止字段停止；超过 100 页报错，不保存截断结果。券码优先取 `couponEntity.memberBenefitId`，其次为 `shortCouponNo`。`AVAILABLE`、`USED`、`EXPIRED` 映射为界面状态，其他值标为未知，不猜测可用。

目前实现验证码登录，不包含脚本中尝试多个请求结构的自动注册分支，也没有凭证刷新接口；登录过期需要重新输入验证码。

## 本站接口

所有接口要求有效站点身份、同源访问及 `x-starbucks-client: 1` 请求头；响应均设置 `Cache-Control: no-store`。

| 方法 | 路径（前缀 `/api/starbucks`） | 请求 |
| --- | --- | --- |
| GET | `/state` | 返回当前用户账号、脱敏卡券及协议配置状态 |
| POST | `/auth/sms` | `{phone}` |
| POST | `/auth/login` | `{phone,pin}` |
| POST | `/accounts/:id/refresh` | 刷新指定账号卡券 |
| POST | `/accounts/:id/codes` | `{ids,activeOnly}`；每批 1–1000 张，默认只允许可用券；查看单张可传 `false` |
| DELETE | `/accounts/:id/remove` | 仅移除本工具保存的数据，不注销星巴克账号 |

成功响应为 `{ok:true,data:...}`，失败响应为 `{ok:false,message,errorCode,requestId}`。上游 HTML、Token 和原始响应不会直接展示到前端。账号按站点用户隔离，其他用户无法查询、导出或删除。

## 运行配置与保存

在应用目录执行：

```sh
npm run starbucks:configure -- '/绝对路径/参考脚本.user.js'
```

命令只提取已知协议字面量，不执行脚本。协议保存在 `data/starbucks/protocol.local`（权限 0600），不提交 Git、不进入前端构建。可通过 `STARBUCKS_PROTOCOL_FILE` 指定位置。更换版本后需要重新导入协议并验证。

账号默认保存在 `data/starbucks/accounts/`，可用 `STARBUCKS_DATA_DIR` 覆盖。每个站点用户使用独立文件，沿用应用的 AES-GCM 加密和 `CMCC_DB_ENCRYPTION_KEY`，目录权限 0700、文件 0600、原子替换。备份和迁移必须一并安全保存应用加密密钥、协议文件和账号数据；不要提交这些文件。解密失败或损坏时拒绝覆盖。

验证码不落盘。浏览器不保存 access token；普通列表不返回完整手机号及券码，只在明确查看或复制时返回选中券码。页面刷新不会自动访问真实上游，刷新卡券与读取过期缓存时才会查询。

## 验证范围

`npm run test:starbucks` 覆盖加密与签名、登录请求结构、凭证兑换、分页、主子券解析、加密存储、身份隔离、异常响应及限流。设置 `STARBUCKS_REFERENCE_SCRIPT` 为原脚本路径，可额外运行与脚本加密实现的黄金向量比对；原脚本不进入仓库。

`npm run test:starbucks-browser` 通过模拟 API 验证 1440、390、320 像素宽度的查询、筛选、登录表单、查看与复制、错误及失效交互。可用 `STARBUCKS_TEST_BASE` 指定已部署域名。

本轮未发送真实星巴克短信，未登录或查询真实星巴克账号；实际官方链路需使用者自行输入手机号和验证码验证。自动化测试通过不代表官方接口不会发生协议变更或风控拒绝。

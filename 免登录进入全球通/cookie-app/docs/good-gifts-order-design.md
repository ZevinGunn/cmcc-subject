# 好礼多多订购产品与实现设计

## 1. 产品位置

两个业务作为 cookie-app“业务订购 > 移动商城”的子业务，与已有套餐和融合权益共存，不新增重复的登录页面或独立权限。入口使用已有 `businessOrder` 权限，公共页面只显示该用户关联账号，管理员页面可使用已启用账号。

## 2. 信息结构与交互

- 业务选择：会员版和流量版使用独立图标、名称和简短内容提示，沿用现有紧凑网格。
- 账号：使用可搜索账号选择器，显示脱敏手机号；SSO 后再次核对手机号。
- 商品：首次查询后展示上游页面名称、全部档位和实时说明；默认选择第一项但不自动提交。
- 校验：选择档位后依次展示规格详情、资格结果、协议和风险提示。
- 操作：只有协议同意且资格通过时可正常发送验证码；资格失败需显式开启“仍尝试提交”。
- 确认：验证码和“确认订购”双重确认，提交按钮保持固定高度并在请求中禁用。
- 结果：成功、失败、待确认分别展示，待确认禁止暗示可立即重试。

界面复用 `V2BenefitOrderWorkflowPage`，保持现有 Apple 风格的即时按压反馈、清晰层级、克制动效和 `prefers-reduced-motion` 行为，不复制微信商品营销页的装饰布局。

## 3. 服务端状态机

```text
authenticated
  -> product_ready       查询个性化页并归一化全部档位
  -> selection_ready     规格详情 + 预检 + 关联活动 + 协议
  -> order_sms_sent      发送验证码并记录 bookTime
  -> ordering            单次在途锁
  -> finished            成功 / 失败 / 结果不确定
```

用户可从 `selection_ready` 或 `order_sms_sent` 返回档位选择；返回时清除档位详情、协议、关联活动、验证码时间和最终结果，保留登录会话与已查询商品。

## 4. 数据设计

`RETAIL_PRODUCT_PRESETS` 新增：

- `pageMode`: `product_code | personal_page`
- `personalPageId`: 个性化页权威标识
- `mergeCode`: 聚合入口标识，仅用于追踪和配置识别
- `sourceParams`: `fromRecommend/pageSource/pageid`

`PremiumSession` 在服务端保存实时 productId/productCode、规格详情、协议、关联活动、bookTime 和加密网关会话。前端只获得脱敏账号、可展示的产品内容和状态，不获得 Cookie、Authorization 或密钥。

## 5. 安全与可靠性

- 路由层在创建会话前校验用户权限、账号归属和 Cookie 可用性。
- 预设业务不接受前端覆盖 personalPageId、pageid 或内部产品号，避免参数越权或错误下单。
- 业务规则 HTML 在前端经过白名单式清理，去掉脚本、表单、事件属性和危险 URL。
- 服务端有短信冷却、阶段校验和订单在途锁。
- 不对超时订单自动重试；会话仅内存短期保存并按 TTL 清理。

## 6. 验证计划

- 单元测试：预设映射、规格归一化、个性化说明、`id` 型协议、嵌套预检响应和账号访问控制。
- UI 测试：两个入口存在，公共/管理员统一页继续复用现有账号与流程组件。
- 静态验证：TypeScript、API 测试、UI 测试、生产构建、`git diff --check`。
- 浏览器验证：桌面与移动宽度检查业务选择、账号搜索、商品加载、错误和禁用状态；只用无副作用或模拟状态，不点击真实短信和订购提交。

## 7. 已知限制

当前提供的 HAR 只包含会员版完整运行样本。流量版的入口和 personalPageId 已明确，实现具备实时查询能力，但其内部商品与档位值必须在有效账号登录后由上游返回。若上游改变数据结构或要求新增风控字段，服务端会返回格式或上游错误，不会使用会员版数据兜底下单。

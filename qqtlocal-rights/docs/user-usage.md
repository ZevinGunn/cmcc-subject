# 项目使用说明

## 1. 快速启动
1. 安装依赖并启动服务：在项目根目录执行 `./run.sh`，脚本会创建 Python 虚拟环境、安装依赖、编译 Go/Java worker（如有）并启动 FastAPI。
2. 打开浏览器访问 `http://localhost:8000/login.html` 进入用户登录页；管理员使用 `http://localhost:8000/admin.html` 登录。

## 2. 用户登录流程
- `login.html` 为纯白、无圆角的简洁页面，只用于用户凭密钥登录；主页不再包含管理员面板。
- 输入密钥后点击「进入系统」会调用 `/api/auth/key/login` 验证，成功后自动跳转到主控制台。
- 如果已经登录过，点击「使用缓存密钥进入」可直接跳转；点击「清除缓存密钥」可以删除本地存储的过期密钥。

## 3. 控制台要点（`index.html`）
- 账号区域：支持粘贴 Token/Cookie 或通过短信登录添加账号，可刷新单个账号状态、查看亲友圈、手动删除。
- 「刷新全部」按钮会批量重新验证所有账号。「🗑 清除全部」按钮则会清空所有本地账号数据、停止当前定时任务、清空日志面板并重置 `localStorage`。
- 「复制日志」会将当前配置、账号列表、定时状态和日志内容合并成纯文本，一键拷贝到剪贴板，便于 QA 记录与优化。
- 日志面板会定期轮询 `logs/` 目录最新文件，默认显示 `等待任务启动...`，可用「清空」按钮抹除当前显示。

## 4. 抢购任务配置
- 基础参数（目标时间、并发、轮询）均在右侧表单填写，实时同步到本地 `qqt_config` 并通过 `saveConfig` 同步至后端。
- 点击「立即执行」会创建一次性任务，名称类似 `Manual-<timestamp>`，后台会立即开始抢购；若选定「开启定时任务」，会在指定小时分钟秒触发一个 cron 任务（名称为“每日自动抢购”）。
- `config` 面板支持服务器时间与本地时间切换、监控模式开关。`监控模式` 会在服务启动前等待目标时间再执行，适合高精度场景。
- 新增「每轮账号间隔」与「每轮账号数」字段：
  * 「每轮账号间隔」控制同一轮中账号请求的发送间隔（默认 10ms），若设置 >0 会让后台以顺序方式发请求并在两次请求之间睡眠此时间，帮助把请求压缩到 10:00:00.050~0.150 这段窗口；
  * 「每轮账号数」限制每次轮询要尝试的账号数量，其余账号将通过轮数轮换来覆盖，避免一次请求超过 5 个账号导致响应分布过宽。建议设置 3~5，搭配 5 次轮询覆盖优先账号。
- 新增「🧪 一键测试」按钮：点击后会自动将目标时间设为当前时间 + 1 分钟、调整轮询参数为 5 次轮询 / 每轮账号数 ≈ 总账号数 ÷ 5 / 每轮间隔 10ms，并直接创建一个只运行一次的测试任务。后台会在日志中加上【测试模式】标记，方便观察黄金窗口效果。
- 测试模式会强制采用顺序执行（即不开启多线程），并额外传递 `force_sequential_run_once` 标志，确保每轮只有一个 `run_once` 按顺序发号请求，避免测试时出现“多线程同时请求同一账号”触发风控的情况。
- 新增「🚀 正式抢购」按钮：点击后会把抢购时间设置为每天 09:59:59（提前一分钟启动监控模式），轮询次数/间隔/账号切片默认 5 次/20ms/每轮 4 个账号，并根据当前有效账号数同步 `accounts_per_poll`；Monitor 模式再加上 Start Delay 850ms，确保第一轮请求实际上仍踩在 10:00:00.050~0.200 内。按钮会自动调用 `saveConfig` 并下发 cron 任务，提示“已经自动下发定时任务”。

## 5. 管理员操作（`admin.html`）
- 管理员需要访问独立页面 `admin.html`，输入账号密码登录后才可查看密钥列表。
- 可在上方表单填入备注、有效期（小时）和自定义密钥，点击「新增密钥」会调用 `/api/admin/keys` 创建。
- 每条密钥都显示创建时间与到期时间，支持「延长 24h」和「删除」操作；刷新按钮会重新拉取全量密钥。
- 退出按钮会清除管理后台的 token，回到登录界面。

## 6. 日志与审计
- 日志写入位置：`logs/<job_id>-YYYYMMDD-HHMMSS.log`，每次任务都会新建文件。`copyLogSnapshot` 会先调用 `/api/logs/<job_id>` 获取最新文件，再把内容与当前配置/账号一起粘贴到剪贴板。
- 建议在每次抢购后保存日志快照，保存内容包括：
  * 当前页面配置（目标时间/延迟/并发/轮询/商品 ID/时间源/监控模式）
  * 账号清单（手机号 + 状态 + 转赠对象）
  * 抢购情况（定时状态、任务 ID、有效账号数量）
  * 详细日志文本

## 7. 其他提示
- 所有任务配置和密钥均保存在 `data/` 目录（`jobs.json`、`auth_keys.json`），可备份或根据需求替换为持久化存储。
- 若需自定义抢购逻辑，可编辑 `backend/qqt_mcyp.py` 的 `run_poll` 实现或增加新的外部 worker（`go-worker`/`java-worker`），只要能通过 `run_external_worker` 接收 JSON 字符串即可接入。

## 8. 日志分析与优化建议
- **2026-01-22 09:59:59** 的日志（`d66750f5357f-20260122-095959.log`）显示抢购轮训在 `09:59:59.911` 即开始发起，第 5 轮约在 `10:00:00.006` 启动。成功协议均在 `10:00:00.114`～`10:00:00.125` 之间返回，RTT 介于 `45ms`～`55ms`，说明真正的成团窗口落在 `10:00:00.050`～`10:00:00.150`。
- **2026-01-23 09:59:59** 的日志（`cb730e67543b-20260123-095959.log`）同样在 `09:59:59.959` 开始筹备，但所有请求都从 `10:00:00.119` 开始扎堆，直到 `10:00:00.245` 才停止，未击中黄金时间段，返回 `无库存` 或 `活动火爆`。平均 RTT 维持在 `43ms`。
- 结论：**黄金窗口极窄（50ms～150ms），请求必须错峰发出**，否则会与平台其他请求撞到一起导致风控或库存耗尽。RTT 平均 40ms 左右，能接受 `p95` 在 60ms 内。

## 9. 推荐抢购配置（20 个账号 / 5 次轮训）
1. **时间定位**：目标时间 `10:00:00`（`小时=10`、`分钟=0`、`秒=0`），`延迟启动 800~850ms`，结合“监控模式”+“北京时间”可把实际请求确定在 `10:00:00.050`～`10:00:00.150`。
2. **轮训节奏**：
   * 轮训次数：`5`；
   * 每轮账号数：`4`（确保 5 轮能覆盖 20 个账号）；
   * 每轮账号间隔：`10ms`（使同一轮请求在 5~50ms 内陆续发出）；
   * 轮训间隔：`15~20ms` （使每轮之间保持微小间隔，避免所有轮同一时间打出）。
3. **并发线程**：`5` 个 worker 足以支撑上述节奏，不必盲目提升线程数以免触发风控。
4. **日志分析工具**：每次任务完成后用“复制日志”导出 `抢购参数 + 账号清单 + 实时日志`，依据日志中 `send_time/recv_time` 衡量上次轮训是否落在窗口内，并把成功 `send_time` 与 `recv_time` 记录下来用作下一次 `start_delay` 微调。
5. **测试模式**：使用“🧪 一键测试”可自动安排 1 分钟后的试跑，系统会根据账号数量自动计算 `每轮账号数` 和 `间隔`，强制串行执行单轮，并在日志中写入 `[测试模式]` 标签，便于验证是否真正控制在 `50~150ms` 区间内。

## 10. 后续优化开发计划
1. **数据闭环**：依据日志中的 `RTT` 和 `返回码`（`-15`/`3`/成功），持续调整 `start_delay`、`poll_interval_ms`，并在 `copyLogSnapshot` 里多记录某轮的第 1/5 个账号 `send_time` 用于分析是否超出窗口。
2. **账号分片策略**：当有效账号超过 20 时，可在 `每轮账号数` 上下浮动（比如设置 `6` ，但配合更短的 `poll_interval` 和 `account_delay`）以确保核心账号仍能在黄金时间抢购。
3. **异地部署/校时**：在不同网络下对比 `system_time` 与 `server_time` 的差异，必要时使用 `北京时间` 并在日志中同步 `latency` 后进行微调，避免卡在 `09:59:59` 前后过久导致窗口错过。
